# M0 checkpoint — Architecture ADR and vertical spike

Status: **passed after independent review**

Date: 2026-08-31

Scope: M0 only; no production runtime cutover

## Outcome

M0 is complete after independent review and remediation. The repository has an accepted
architecture decision, current-system and ownership inventories, an explicit threat model, and an
isolated Rust vertical spike. The spike exercises the risky trusted-core path without changing the
Python application's runtime, API, data, or user-facing behavior.

The next executable phase is M1. The spike is evidence, not the production workspace or a
shortcut around the M1 protocol work.

## Exit-criteria evidence

| Criterion | Evidence |
|---|---|
| IPC does not duplicate the complete internal model | The worker protocol carries only a minimal request plus typed content/tool-intent messages; trusted run, approval, capability, and event state stay in the Rust core. |
| Worker crash preserves the log and cannot bypass approval | `worker_crash_and_output_limits_are_terminal` persists `worker.failed` and `run.failed`, restarts the app-server over the same disposable DB, and replays terminal state for crash, oversized-frame and message-flood cases. |
| Worker output reaches the protocol before completion | `worker_events_stream_before_delayed_worker_finishes` observes a durable `content.delta` before a deliberately delayed worker can return its tool intent or command response. |
| Client delivery cannot stall or cancel durable execution | `client_disconnect_does_not_cancel_durable_execution` and `blocked_writer_is_timed_out_without_blocking_durable_execution` cover BrokenPipe and an `AsyncWrite` that remains pending forever. The core completes independently; restart/same-key lookup returns the durable receipt without another worker attempt. |
| Live and replayed client state are identical | `approval_replay_idempotency_and_catchup_are_consistent` compares the streamed event sequence and reducer state with `run.events` replay. |
| Repeated mutating commands do not duplicate effects | Prompt and approval commands persist actor/method/key, canonical SHA-256 request fingerprint and original receipt. Identical retries return that receipt; changed inputs return `idempotency_conflict`. Tool effects verify run/tool/argument identity. |
| Approval completion is crash-consistent | `approval_transaction_rolls_back_at_every_failpoint` reopens the DB after injected failures following the approval update, resolved event, effect and terminal writes. Every partial attempt rolls back and the same command then completes exactly once. |
| Cursor reconnect loses no durable events | `run.catchup` returns the persisted suffix after `afterSeq`; the test compares it with the corresponding replay suffix. Live catch-up-to-tail handoff is deliberately deferred rather than claimed by M0. |
| Identity and capability checks remain trusted | Parameter structs reject client `actor` and `grantedCapabilities`; local stdio derives `local:stdio-owner`, while `--allow-write` is server configuration. `server_owned_capability_rejects_client_grants_and_malformed_intents` proves denial and argument validation occur before approval/effect. |
| Disposable DB isolation is enforced | The store requires a spike-specific SQLite application id and schema sentinel, and `foreign_database_and_protocol_contract_are_rejected_safely` rejects an unrelated non-empty database. |
| Production rewrite scope is explicit | ADR section “What must be rewritten after M0” excludes the spike binary, schema, worker, transport, store, and fixed local actor from production reuse without the planned hardening. |

The executable evidence is in
[`spikes/m0-rust-core/tests/vertical.rs`](../../../spikes/m0-rust-core/tests/vertical.rs).
All spike databases are created under `tempfile::TempDir`; the harness never opens the current
application database.

## Compatibility and data safety

- The existing FastAPI/React runtime remains the only production path; no endpoint, WebSocket/SSE
  shape, SQLModel, Alembic migration, config format, secret ciphertext, or project key changed.
- The M0 store is deliberately disposable and schema-incompatible with the production database.
  Its application id and sentinel cause foreign non-empty SQLite files to fail closed.
- Existing Fernet data stays owned by Python until the migration phase that implements dual-read,
  verified migration, backup, and rollback.
- `local` remains the default single-user profile. `server`/VPS and `telegram` are architectural
  profiles only in M0; neither is exposed by the spike.

## Security conclusions

- The Rust process, not the worker or protocol client, owns capability enforcement, approval
  revision checks, event sequence allocation, terminal transitions, and tool-effect deduplication.
- Approval decision, in-database marker effect, terminal run state, durable events and command
  receipt commit in one `BEGIN IMMEDIATE` transaction; injected failure rolls the entire unit back.
- Worker failure is converted into durable terminal events, including spawn/transport failure.
- Local stdio identity is server-derived. Production server and Telegram identities must be
  authenticated at their adapters and cannot be accepted from request payloads.
- The spike does not claim production sandboxing, TLS, origin/CSRF enforcement, Telegram
  `initData` validation, multi-user authorization, or untrusted extension execution.

## Independent review

The first independent read-only review inspected the actual diff and rejected the initial
checkpoint as insufficient. It reported four P1, four P2 and one P3 findings:

- client-controlled capabilities;
- non-atomic approval/effect/event completion;
- idempotency keys without request fingerprints or original receipts;
- batched worker output and a snapshot incorrectly named as live subscription;
- tool argument validation after approval;
- silent tool-effect identity collisions;
- documentation-only disposable DB protection;
- unbounded protocol/worker input;
- incorrect JSON-RPC method-not-found mapping.

All nine initial findings are addressed in code and tests. The second pass additionally found
transport cancellation, non-atomic prompt approval preparation and a flaky absolute timing test;
the third found slow-writer backpressure. Remediation added transport-independent execution,
atomic prompt preparation with five rollback failpoints, relative streaming-order evidence and a
delivery deadline tested with a permanently pending writer.

The final independent read-only pass found no actionable P0-P3 findings. The reviewer independently
ran Rust format, clippy, all 10 integration tests and build successfully, and confirmed the review
gate passed.

Accepted M0 residual risks are limited to the declared spike boundary:

- one fixed local actor and static CLI policy;
- an in-SQLite marker effect rather than an external-effect outbox/reconciler;
- snapshot `run.catchup`, not multi-subscriber live tail or gap-free live handoff;
- a scripted worker without production handshake, environment allowlist or sandbox;
- no production SQLite owner queue, migrations, secret compatibility or concurrent runtime;
- incomplete prompt recovery is triggered by same-key retry, not a startup sweep;
- fixed delivery/worker deadlines rather than negotiated production limits.
