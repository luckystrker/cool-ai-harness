# M10 checkpoint — Store and background subsystems parity

Status: **passed**

Date: 2026-09-19

Scope: Rust ownership of the existing Python SQLite schema at the cutover baseline (adoption,
backup/restore, migration ownership), typed stores for every legacy subsystem, scheduler
restart/catch-up/misfire/overlap semantics, memory retrieval/lifecycle parity, inspector timeline
projection, cross-language contract tests, and the typed App Protocol command/query families for
the React surface inventory plus the generated-SDK contract coverage test.

## Decisions

- **Legacy store wiring.** `ServerConfig` gained `legacy_store: Option<Arc<LegacyStore>>` and
  `secrets: Option<Arc<SecretKeyring>>`. The app server keeps the M9 `DurableStore` for sessions,
  runs and canonical events and serves the legacy families from the adopted `harness.db` when the
  store is configured; without it those commands fail closed with `legacy_store_unavailable`.
  The CLI opens `harness.db` only through the explicit `cool app-server --legacy-store` flag, and
  only read-only unless the file is already Rust-owned, so starting a server can never adopt a
  Python store implicitly.
- **Idempotency.** The legacy schema has no idempotency columns, so Rust owns
  `rust_idempotency` (migration v2). Mutations run reserve → execute → complete; a replay with the
  same actor/key/fingerprint returns the stored result, a different fingerprint or a still-pending
  reservation fails closed with a conflict. This is at-most-once; TTL/GC of pending rows is
  deferred.
- **Secrets.** Provider `api_key` input is encrypted through `SecretKeyring` (fail closed with
  `secret_key_unavailable` without a keyring); protocol records never expose provider keys or
  webhook secrets, and record bridging ignores unknown store columns. `ServerConfig` has a manual
  `Debug` that only reports secret presence.

## Implemented (store and background parity)

- New crate `crates/cool-store` (~106 tests) that opens the real `harness.db`:
  - baseline detection and one-way **adoption** with an atomic ownership marker in
    `rust_store_meta` (`owner`, `adopted_alembic_revision`, `adopted_at`, `backup_path`),
  - verified pre-adoption backup (`VACUUM INTO`, `PRAGMA integrity_check`, revision and row-count
    comparison) and standalone-verified restore (baseline check, `-wal`/`-shm` removal before and
    after replacement),
  - incremental, resumable Rust migrations (`rust_store_meta.schema_version`) that run after
    adoption and resume after an interrupted step,
  - fail-closed ownership semantics: a changed `alembic_version` on a Rust-owned store raises
    `MigrationOwnershipConflict`; `read_only` mode opens Python data without adopting or writing.
- Baseline snapshot `crates/cool-store/tests/fixtures/python_schema_0022.sql` generated from the
  real Alembic chain by `backend/tests/schema_snapshot.py`, with a deterministic semantic
  fingerprint (`*.fingerprint.json`) and SHA-256 manifest.
- Python-side competition guards: `backend/app/core/db.py` (`init_db` and `_run_alembic_upgrade`)
  and `backend/alembic/env.py` (`run_migrations_online`) both refuse a store owned by Rust.
- Typed stores over the legacy schema: conversations/messages/runs/run-events/tool-calls/approval
  audits, artifacts metadata, budgets/spend, analytics aggregations, tasks/task-runs, RSS,
  webhooks, wiki, profiles/plans/subagents/macro tools, memory records/entities/working memory,
  research runs, providers.
- Deterministic scheduler engine (`crates/cool-store/src/scheduler.rs`): 5-field cron with
  names/ranges/steps, UTC/fixed-offset timezones (IANA names fail closed), quiet-hours gating,
  misfire grace/policy, coalescing, overlap suppression, catch-up and failure-count auto-disable.
- Memory retrieval parity (`crates/cool-store/src/memory.rs`) against the real Python
  `app.memory.retrieval` ranking (FTS5 + preference/entity legs + composite rerank), plus
  lifecycle sweeps; parity fixture generated by the Python runtime.
- Inspector projection (`crates/cool-store/src/observability.rs`) building the run timeline and
  run comparison from the event log, verified against a Python-generated fixture.
- Rust runtime visibility: `cool doctor --data-dir <path>` reports the legacy store status
  (absent / python-owned / rust-owned, Alembic revision, Rust schema version, adoption time)
  without adopting or writing.
- CI job `store-parity` (Rust toolchain + backend deps) running the cross-language tests.

## Implemented (protocol surface and SDK coverage)

- `crates/cool-protocol/src/families/{mod,content,knowledge,ops}.rs`: typed params and result
  records for every legacy family — conversations (incl. backend-only search/bulk), runs, memory,
  entities, plans, subagents, inspector, budgets, artifacts, workspace, profiles, analytics,

  legacy command variants; the 12 M9 commands and all golden traces are unchanged.

  issues SQL. Every typed call goes through actor-scoped `cool-store` methods; mutations use
  `run_idempotent` (or the async variant for the workspace git capability); errors map to the

  directories/git run with path validation and a 5 s timeout.

  `sdk | static/blob | sse/stream | deferred` and a rationale for every exception.

  from the TypeScript sources, cross-checks the inventory in both directions, and for every `sdk`
  entry requires a generated `Command` method, a paired `CoolSdk` member whose name equals the
  derived camelCase command name, and a real `Command::<Variant>(...)` dispatch arm in the app
  server. Exception statuses require a recorded rationale.
- `sdk/typescript/src/client.ts`: hand-written `CoolSdk` with one typed method per generated
  command (144), compiled by `npm run protocol:check` via the SDK `tsconfig` (previously the
  hand-written client was not typechecked).
- Store additions used by the protocol layer, each with tests: `run_idempotent`(+async),
  `budget_status` calendar windows, `update_plan_draft`, `seed_builtin_profiles`,
  `count_unread_task_runs`, `recent_working_directories`, wiki tag filter, filtered artifact and
  webhook-event reads, `cron_next_runs`, `explain_memory`, `latest_schema_version`.

## Compatibility

- The Python schema at Alembic revision `0022` is the frozen baseline; every supported revision has
  a committed snapshot and a drift check. Rust never runs Alembic and never changes
  `alembic_version`. Rust migration v2 adds only the Rust-owned `rust_idempotency` table;
  `latest_schema_version()` keeps the adoption tests version-agnostic.
- Rust replicates the Python engine pragmas (`WAL`, `synchronous=NORMAL`, `busy_timeout=5000`) and
  explicitly disables `PRAGMA foreign_keys` because the Python runtime leaves them off; delete
  semantics (including orphaned historical rows) therefore match.
- Legacy `run_events.seq` starts at 0 in both runtimes; SQLAlchemy datetime text format
  (`YYYY-MM-DD HH:MM:SS.ffffff`) is used for all Rust-written timestamps.
- The M9 App Protocol v1 surface and `plugins.lock.json` are unchanged: the 12 core commands and
  the 12 golden traces are byte-identical. New command variants are additive; a client that does
  not know them never sees them.
- The SDK member-name convention (camelCase of `family.operation`, `_` splits into words) is part
  of the committed coverage contract for future commands.
- Protocol records are camelCase mirrors of the store records; JSON columns (`metadata`,
  `settings`, `arguments`, ...) pass through opaquely. Records deliberately omit the provider key
  and webhook secret columns and ignore unknown store fields.
- `cool doctor` output gained `legacyStore`; `phase` reports `M10`. The CLI test was updated
  accordingly; `cool app-server --legacy-store` is the only way to serve the legacy families.

## Data and security

- Adoption takes a verified backup **before** the store switches journal pragmas or writes anything;
  the ownership markers commit atomically, so an interrupted adoption is resumable rather than
  bricking the database.
- Restore rejects backups that are not at the supported baseline and removes stale WAL sidecars
  before replacing the file, so a previous WAL cannot replay over restored data.
- Actor scoping: every typed read/write resolves the actor through `rust_actors` (or the read-only
  fallback for un-adopted Python data) and validates conversation/user ownership; there is no
  implicit `user_id = 1` on the write path. The app-server dispatcher always uses the
  transport-authenticated local actor; a second actor's rows are invisible
  (`legacy_surface.rs::conversations_crud_is_idempotent_and_actor_scoped`).
- Idempotency: `rust_idempotency` is keyed by `(actor_id, method, idempotency_key)`; replays return
  the stored result, mismatched fingerprints and pending reservations fail closed. Idempotency
  keys are bounded to 256 chars. Failed actions leave a pending row (documented at-most-once).
- Secrets: provider `api_key` is encrypted with `SecretKeyring`; without a keyring the write fails
  closed instead of storing plaintext. Provider keys and webhook secrets are absent from protocol
  records, and `ServerConfig`'s manual `Debug` prints only their presence. The webhook secret is
  generated by the store and intentionally never returned over the protocol.
- Scheduler IANA timezone names fail closed (`UnsupportedTimezone`) instead of silently running at
  the wrong local time; UTC and fixed offsets are supported.
- Workspace git commands validate the target directory, run with a 5 s timeout, and are not SQL
  access; `git_checkout` goes through the async idempotency reservation.
- Every memory/analytics/task query is bounded; no new `unsafe` code (workspace forbids it).

## Independent review

First pass `m10_protocol_review` (read-only, not the author) inspected the full diff and untracked
files, ran the targeted suites, and falsified parts of the original coverage gate. Findings and
resolutions:

1. **P1 — SDK check was a string search.** A stray `method: "..."` literal passed even with the
   method deleted. Fixed: coverage pairs each `CoolSdk` member with its same-line command literal,
   derives the expected camelCase member name, rejects duplicates, and fails on mismatch
   (falsified again: renaming a method fails the gate).
2. **P1 — dispatch honesty was ungated.** Added a dispatch cross-check deriving
   `Command::<RustVariant>(...)` from each sdk command and requiring it in the app-server sources.
3. **P1 — runtime-divergent operations were marked sdk.** `providers.listModels`,
   `subagents.launch/launchBatch`, `research.start/cancel/rerun`, `tasks.runNow`,
   `tasks.scheduler`, `webhooks.replay` are now `deferred` with per-operation rationales: the
   typed commands and durable store effects exist, while execution/engine/live-probe wiring is
   M11.
4. **P2 — contract mismatches with the frontend.** `SubagentLaunchParams/Item` gained `model`,
   batch input field renamed to `items`, `subagents.runs_cancel` returns
   `{ runId, cancelled }`, `research.cancel` returns `{ cancelled }`. Generated types, SDK,
   dispatch and tests updated.
5. **P2 — `memory.pending` offset, `conversations.bulk` semantics, discovery parser shapes,
   `tasks.parse_cron` natural language, fabricated `tasks.scheduler` constants.** All fixed or
   reclassified; a natural-language subset of `parse_natural_schedule` is now ported (EN/RU).
6. **P3 — `git_checkout` bypassed idempotency; unbounded idempotency keys.** Fixed with
   `run_idempotent_async` and the 256-char limit. Pending-row TTL/GC and Python-readability of
   versioned provider keys are recorded as residual risks below.

Second pass `m10_followup_review` verified the fixes against the code and reran the suites:
all numbered points PASS; two low-severity gate notes (dispatch substring match, operation
discovery shape sensitivity) were fixed afterwards (`Command::<Variant>(`, control-keyword
denylist), and the low findings were closed with no open P0-P2 issues.

## Residual risks

- The cross-language tests run in CI's `store-parity` job; the plain backend job skips them when
  `cargo` is unavailable (`cargo_required` marker), so the backend job alone is not evidence.
- Memory BM25 ranks match Python within 1 ULP because rusqlite's bundled SQLite and the Python
  build differ slightly; the committed fixture keeps the Python values for future diffing.
- `restore_backup` cannot distinguish hard-linked backup/target files; the copy-to-staging path
  still preserves the backup inode, so this is not a data-loss path.
- `record_skipped_run` advances `next_run_at` from "now", matching Python's `compute_next_run`
  basis; cron schedules therefore resume from the current time rather than replaying missed slots.
- A failed idempotent mutation leaves a permanent `pending` reservation; the same key then fails
  closed until an operator clears the row. This is the documented at-most-once contract.
- Rust writes provider keys in the M6 versioned envelope, which the Python Fernet reader cannot
  read; Rust reads Python's raw Fernet tokens, and Python refuses Rust-owned stores, so there is
  no cross-runtime handoff of these rows in M10.
- `conversations.compact` uses a deterministic extractive summary until the M11 provider runtime
  replaces it with LLM summarization; message counts and cutoffs match Python.
- `tasks.parse_cron` ports a subset of the Python natural-language phrasings (interval, weekday
  sets, named weekdays EN/RU, monthly/weekly/daily, bare time, meridiem); other phrasings return
  the explicit "could not interpret" detail, never a wrong schedule.
- The protocol coverage gate's operation discovery is source-shape based (two-space object
  members); a reformatting change would fail loudly (no matching source) rather than silently
  reduce coverage.
