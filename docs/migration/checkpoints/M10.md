# M10 checkpoint — Store and background subsystems parity

Status: **in progress** (store/background parity passed; protocol surface pending)

Date: 2026-09-19

Scope: Rust ownership of the existing Python SQLite schema at the cutover baseline (adoption,
backup/restore, migration ownership), typed stores for every legacy subsystem, scheduler
restart/catch-up/misfire/overlap semantics, memory retrieval/lifecycle parity, inspector timeline
projection, and cross-language contract tests. The typed App Protocol command/query handlers for
every React surface and the generated-SDK coverage test are **not** complete; the phase stays
in progress until they are.

## Implemented

- New crate `crates/cool-store` (~106 tests) that opens the real `harness.db`:
  - baseline detection and one-way **adoption** with an atomic ownership marker in
    `rust_store_meta` (`owner`, `adopted_alembic_revision`, `adopted_at`, `backup_path`),
  - verified pre-adoption backup (`VACUUM INTO`, `PRAGMA integrity_check`, revision and row-count
    comparison) and standalone-verified restore (baseline check, `-wal`/`-shm` removal before and
    after replacement),
  - incremental, resumable Rust migrations (`rust_store_meta.schema_version`) that run after
    adoption and resume after an interrupted step,
  - fail-closed ownership semantics: a changed `alembic_version` on a Rust-owned store raises
    `MigrationOwnershipConflict`; `read_only` mode opens Python data without adopting or writing.
- Baseline snapshot `crates/cool-store/tests/fixtures/python_schema_0022.sql` generated from the
  real Alembic chain by `backend/tests/schema_snapshot.py`, with a deterministic semantic
  fingerprint (`*.fingerprint.json`) and SHA-256 manifest.
- Python-side competition guards: `backend/app/core/db.py` (`init_db` and `_run_alembic_upgrade`)
  and `backend/alembic/env.py` (`run_migrations_online`) both refuse a store owned by Rust.
- Typed stores over the legacy schema: conversations/messages/runs/run-events/tool-calls/approval
  audits, artifacts metadata, budgets/spend, analytics aggregations, tasks/task-runs, RSS,
  webhooks, wiki, profiles/plans/subagents/macro tools, memory records/entities/working memory,
  research runs, providers.
- Deterministic scheduler engine (`crates/cool-store/src/scheduler.rs`): 5-field cron with
  names/ranges/steps, UTC/fixed-offset timezones (IANA names fail closed), quiet-hours gating,
  misfire grace/policy, coalescing, overlap suppression, catch-up and failure-count auto-disable.
- Memory retrieval parity (`crates/cool-store/src/memory.rs`) against the real Python
  `app.memory.retrieval` ranking (FTS5 + preference/entity legs + composite rerank), plus
  lifecycle sweeps; parity fixture generated by the Python runtime.
- Inspector projection (`crates/cool-store/src/observability.rs`) building the run timeline and
  run comparison from the event log, verified against a Python-generated fixture.
- Rust runtime visibility: `cool doctor --data-dir <path>` reports the legacy store status
  (absent / python-owned / rust-owned, Alembic revision, Rust schema version, adoption time)
  without adopting or writing.
- CI job `store-parity` (Rust toolchain + backend deps) running the cross-language tests.

## Compatibility

- The Python schema at Alembic revision `0022` is the frozen baseline; every supported revision has
  a committed snapshot and a drift check. Rust never runs Alembic and never changes
  `alembic_version`.
- Rust replicates the Python engine pragmas (`WAL`, `synchronous=NORMAL`, `busy_timeout=5000`) and
  explicitly disables `PRAGMA foreign_keys` because the Python runtime leaves them off; delete
  semantics (including orphaned historical rows) therefore match.
- Legacy `run_events.seq` starts at 0 in both runtimes; SQLAlchemy datetime text format
  (`YYYY-MM-DD HH:MM:SS.ffffff`) is used for all Rust-written timestamps.
- `plugins.lock.json` and the M3-M9 App Protocol v1 surface are unchanged.
- `cool doctor` output gained `legacyStore`; `phase` now reports `M10`. The CLI test was updated
  accordingly.

## Data and security

- Adoption takes a verified backup **before** the store switches journal pragmas or writes anything;
  the ownership markers commit atomically, so an interrupted adoption is resumable rather than
  bricking the database.
- Restore rejects backups that are not at the supported baseline and removes stale WAL sidecars
  before replacing the file, so a previous WAL cannot replay over restored data.
- Actor scoping: every typed read/write resolves the actor through `rust_actors` (or the read-only
  fallback for un-adopted Python data) and validates conversation/user ownership; there is no
  implicit `user_id = 1` on the write path. `with_connection` is a documented test/diagnostics
  escape hatch.
- Secrets: provider `api_key_encrypted` and webhook `secret` are passed through opaquely and are
  redacted in `Debug` output for both read models and request payloads. No decrypt path exists in
  `cool-store`.
- Scheduler IANA timezone names fail closed (`UnsupportedTimezone`) instead of silently running at
  the wrong local time; UTC and fixed offsets are supported.
- Every memory/analytics/task query is bounded; no new `unsafe` code (workspace forbids it).

## Independent review

Reviewer `m10_independent_review` (read-only, did not author the changes) inspected the full diff
and untracked crate, independently reproduced the Python memory-retrieval fixture, and ran the
targeted Rust/Python suites. Findings and resolutions:

1. **P1 — Alembic CLI bypassed the ownership guard.** Fixed: `alembic/env.py` refuses Rust-owned
   databases on a separate read-only connection. The first attempt used SQLAlchemy `inspect()` on
   the migration connection and silently produced partial migrations; the snapshot drift test
   caught it and the guard now uses a short-lived read-only sqlite3 connection.
2. **P2 — `run_events.seq` started at 1 (Python starts at 0).** Fixed and covered by
   `tests/runs.rs`.
3. **P2 — skipped runs did not advance `next_run_at`.** Fixed in `record_skipped_run` with a
   regression test.
4. **P2 — scheduler ignored quiet hours.** Fixed in `Scheduler::plan` with a gating test that
   mirrors Python's reason string and ordering.
5. **P2 — unscoped `get_message`/`get_tool_call`.** Fixed to require actor ownership; NULL-owner
   legacy tool calls are intentionally unreadable.
6. **P2 — interrupted adoption could leave a Rust-opaque database.** Fixed: marker, table and
   revision commit in one `IMMEDIATE` transaction; partial markers resume or fail closed with a
   dedicated test.
7. **P2 — restore verification was self-referential; WAL sidecars removed too late.** Fixed:
   standalone `inspect_backup`, baseline enforcement, same-file rejection and pre-/post-replacement
   sidecar cleanup.
8. **P3 — WAL pragma before backup, stale comments, secret-bearing `Debug` output, offset grammar
   drift.** All fixed; redaction and grammar have tests.

Second pass `m10_review_followup` verified all ten fixes against the code and reran the suites;
third pass `m10_review_residual` verified the follow-up fixes (atomic initialize, immediate
transactions, canonicalized same-file check, NULL-owner rejection, input-type redaction, offset
grammar) and found no P0-P2 issues. Residual P3 notes were addressed by tests for alias restore,
`get_tool_call` scoping and input redaction.

## Residual risks

- The cross-language tests run in CI's `store-parity` job; the plain backend job skips them when
  `cargo` is unavailable (`cargo_required` marker), so the backend job alone is not evidence.
- Memory BM25 ranks match Python within 1 ULP because rusqlite's bundled SQLite and the Python
  build differ slightly; the committed fixture keeps the Python values for future diffing.
- `restore_backup` cannot distinguish hard-linked backup/target files; the copy-to-staging path
  still preserves the backup inode, so this is not a data-loss path.
- `record_skipped_run` advances `next_run_at` from "now", matching Python's `compute_next_run`
  basis; cron schedules therefore resume from the current time rather than replaying missed slots.
