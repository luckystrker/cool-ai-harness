# M11 checkpoint — Web cutover and compatibility workers

Status: **in progress (partial)**. The Rust HTTP/App Protocol facade and the
`cool serve` entrypoint are implemented and covered by tests, and the chat
cutover foundations (conversation -> session binding with canonical transcript
import, run listing, paginated legacy transcript reads) plus the canonical
prompt inputs, durable history cursor and live-run fan-out are implemented on
the Rust side. The React **chat** surface is now switched onto the generated
`CoolSdk`/`HttpTransport` boundary (`conversations`, canonical
`session.prompt` + `streamRunEvents`, `approval.resolve`), and `session.history`
was enriched so the persisted transcript can render without the legacy
`messages` table. The other React API subsystems, the Telegram adapter, the
OpenCode Bun / Python workers, the worker-review UI and the end-to-end
packaging/upgrade suite are **not** done, so the phase stays `[~]` and must not
be treated as complete.

Date: 2026-09-19

Increment 1 (previous session): a browser-facing HTTP/SSE projection of the
App Protocol served by the Rust binary (`cool serve`), with the `local`/`server`
deployment profiles enforced fail-closed, canonical cursor/reconnect event
streaming, and a fetch/SSE transport added to the generated TypeScript SDK.

Increment 2 (previous session) — chat cutover foundations: legacy conversations
now bind to durable Rust sessions through `session.for_conversation`, their
transcript is projected once into the canonical event log, and the bounded reads
the chat surface needs (`session.runs`, `conversations.messages`) exist. The
React `src/api` swap onto these commands is still pending; that increment landed
the Rust runtime/protocol side plus its tests.

Increment 3 (previous session) — close the three Rust gaps that blocked the
React chat cutover: `session.prompt` now carries canonical `planMode`/`systemPrompt`
inputs (planning mode is runtime-owned), `session.history` has a durable
`beforeCursor`/`nextCursor` pagination model, and the new `run.subscribe`
command fans a live run's events out to a second connection. This increment is
additive at App Protocol v1 and leaves the React `src/api` swap, Telegram,
workers and packaging for later increments.

Increment 4 (this session) — switch the React **chat** surface onto the Rust
facade. `frontend/src/api` gained the singleton `CoolSdk`/`HttpTransport`
boundary (`sdk.ts`), `conversationsApi` now composes conversation metadata with
the canonical `session.history` transcript (Rust never writes the legacy
`messages` table), and `useConversationStream` drives a turn through
`session.for_conversation` -> `session.prompt` -> `streamRunEvents` with
`approval.resolve` and `run.cancel`. Because the UI needs persisted-transcript
fields the canonical command did not expose, `HistoryItem` was enriched
(`cursor`/`occurredAt`/`runId`/`model`/`usage`), `PlanCreated` gained the full
`steps` list, and the history pagination boundary was hardened. The remaining
React subsystems (providers/settings, plans, subagents, tasks, research, MCP,
skills, memory beyond the already-typed store commands, ...) are still on the
Python REST/WS path; Telegram, workers and packaging remain pending.

## Implemented

- New crate `crates/cool-http` (M11 §"Web cutover"):
  - `HttpFacade` wraps the existing `AppServer` without owning any agent,
    store or policy logic. Each browser identity is one in-process App
    Protocol connection: `AppServer::serve_io` runs over a `tokio::io::duplex`
    pipe and is driven by the existing `AppClient` (`ConnectionPool`), so the
    HTTP layer sees exactly the stdio/TUI/ACP request/response and live-event
    semantics. Connection creation runs outside the pool lock; the pool is
    capped at 128 live identities and refuses new ones with `503` instead of
    evicting a connection that could own a run.
  - `GET /api/health` — public liveness/phase/capabilities document.
  - `POST /api/rpc` — accepts the canonical `RpcRequest` and returns the
    canonical `ServerFrame` (`RpcSuccess`/`RpcFailure`) with the request id
    echoed, so no HTTP-specific business model is introduced. Only a parse
    failure or an unavailable protocol connection uses a small structured
    transport error; command errors stay canonical `RpcFailure`.
  - `GET /api/events?runId&afterSeq&limit` — SSE stream with canonical
    cursor/reconnect semantics: subscribe → durable catch-up via `run.events`
    → live tail filtered by `seq`, re-catch-up on `Lagged`, `Last-Event-ID`
    precedence over `afterSeq`, and `end` on terminal. Payloads are
    re-projected (a bare `EventEnvelope` for `run.event`, the protocol
    `StreamKeepalive`/`StreamEnd` payloads for keepalive/end), not the tagged
    `StreamFrame` enum. `limit` is clamped to the server-configured
    `event_page_limit` so the facade never requests a page the runtime rejects.
    A client that reconnects with a past cursor cannot double-apply an event.
    An unauthenticated request that would mint a brand-new identity is refused
    (`403 client_identity_required`) unless a token is configured, so a
    cross-site no-cors GET (no Origin, no SameSite cookie) cannot spawn
    connections.
  - Production React assets are served from `--assets` with an SPA
    `index.html` fallback (tower-http `ServeDir::fallback`); without assets
    the root returns a diagnostic placeholder.
- Deployment profiles (`crates/cool-http/src/auth.rs`), fail-closed at startup:
  - `local` (default): loopback-only peer enforcement, optional shared token,
    loopback Origin allowlist that is enforced whenever an Origin is present
    (reads and mutations), non-loopback bind refused without `--allow-remote`
    **and** a token. A present-but-unparseable Origin (`null`, empty, opaque)
    and duplicate `Origin` headers are rejected rather than treated as "no
    Origin"; IPv6 loopback origins (`http://[::1]:…`) are accepted.
  - `server`: token mandatory, `--tls-terminated`/`--trusted-proxy` boundary
    mandatory, `--public-url` mandatory, exact-Origin enforcement whenever an
    Origin is present plus a required Origin on mutations, `Secure` client
    cookie.
  - Token auth accepts `Authorization: Bearer`, `?token=` (for native
    `EventSource`) and a cookie, compared in constant time; client identities
    are generated, validated, and persisted in an HttpOnly `SameSite=Strict`
    `cool_client` cookie. A valid `x-cool-client` header wins, but an invalid
    header no longer shadows a valid cookie.
- `cool serve` CLI command (`crates/cool-cli`): `--data-dir`, `--bind`,
  `--port`, `--assets`, `--profile`, `--token`, `--public-url`,
  `--trusted-proxy`, `--tls-terminated`, `--allow-remote`, `--legacy-store`;
  reuses `build_server` so `--legacy-store` serves the typed legacy families.
  `cool doctor` now reports `phase: M11`, `webFacade`,
  `serveProfiles: ["local","server"]`.
- `sdk/typescript/src/http.ts`: `HttpTransport` (commands over `POST /api/rpc`)
  and `streamRunEvents` (async SSE iterator) implementing the existing
  `CoolTransport` contract. Both send the token via `Authorization`, never
  `?token=`, and the header documents that Node callers must reuse one
  `clientId` across a transport and its event stream. Typechecked by
  `npm run protocol:check`.

### Increment 2 — chat cutover foundations (Rust side)

- `session.for_conversation` (`crates/cool-protocol/src/lib.rs`): find-or-create
  the durable Rust session bound to one legacy conversation. The first call
  creates `rust_conversation_links(conversation_id, actor_id, session_id)` in
  `rust-core.db` (SCHEMA_VERSION 1 -> 2, additive) and an import run that
  projects the legacy transcript into the canonical event log
  (`run.started` mode `import` -> items/tool results -> `run.completed` reason
  `import`). No legacy table is written: this is a one-way projection, not a
  dual write. Replays answer from the durable idempotency record before the
  legacy store is touched, so repeating the command is cheap and still returns
  the original result after the source conversation was deleted. A link owned
  by another actor fails closed (`ActorMismatch` -> `resource_not_found`).
- History projection (`crates/cool-app-server/src/lib.rs`): user/assistant
  rows become `item.completed` (assistant `thinking` becomes `reasoning.delta`
  first), assistant `tool_calls` become `ToolRequested`s, tool rows become
  `tool.completed` or `tool.failed` (`is_error`), and assistant calls without a
  persisted result are backfilled as `tool.failed` (`legacy_tool_unanswered`),
  mirroring the Python `_backfill_missing_tool_results` so the imported history
  is a provider-valid transcript. Result rows match pending calls by stored
  id, then by a unique name, then by the only pending call; missing names/ids
  degrade to stable synthetic values instead of dropping rows. Legacy
  timestamps are normalized to RFC3339. Structurally invalid JSON in a legacy
  column still fails the read closed (strict store parsing).
- Bounded reads: `crates/cool-store` adds `RecentMessages`
  (`LegacyStore::recent_messages`) — one `ORDER BY id DESC LIMIT limit+1` query
  returning the newest window oldest-first plus `has_more`, bounded at
  10 000 rows — so linking never scans a whole transcript. `session.runs`
  lists durable runs of one actor-owned session newest-first (bounded by
  `event_page_limit`). `conversations.messages` is a paginated legacy
  transcript read (`before_id`, limit 1..=2000; out-of-range limits are
  rejected). Leading orphan tool rows are trimmed from the import window and
  `SessionConversationResult.truncated` reports that the projection is not the
  complete transcript.
- `rust_runs.finish_reason` is now populated for terminal events, derived from
  the *masked* envelope so a secret in a terminal/cancel reason cannot outlive
  the event log in run summaries.
- Generated artifacts regenerated from the Rust types: JSON Schema, both
  `cool_protocol.ts` copies, and the typed SDK gained
  `sessionForConversation`, `sessionRuns`, `conversationsMessages`.

### Increment 3 — canonical prompt inputs, history cursor, run fan-out

- `session.prompt` params gained `planMode` and `systemPrompt`
  (`crates/cool-protocol/src/lib.rs`). `AgentRequest` gained a `mode` field
  (`crates/cool-agent/src/loop_runtime.rs`) that is surfaced on `run.started`.
  In planning mode the app-server shadows any caller `systemPrompt` with the
  runtime-owned `PLANNING_SYSTEM_PROMPT` (`crates/cool-agent/src/context.rs`)
  and marks the run mode `plan`; the trusted `update_plan` tool still projects
  `plan.created` / `plan.step_*` events, so planning is provider-driven rather
  than a Python-only code path. Non-planning turns forward the caller system
  prompt; the prompt is used only for the model request and never persisted.
- `session.history` gained durable pagination: params carry `beforeCursor`
  (exclusive) and the result carries `nextCursor`/`hasMore`
  (`crates/cool-protocol/src/lib.rs`). The new
  `DurableStore::session_event_window` (`crates/cool-state/src/lib.rs`) pages
  on the append-only `rust_events.rowid` newest-first with `limit + 1` rows, so
  the read is bounded and never scans the whole log. `session_history` walks
  event chunks until the window begins at a history-group boundary (an
  item/tool event, never a `content.delta`/`reasoning.delta`), so a run of
  deltas is never split from the item it belongs to and `nextCursor` always
  points at a group start. A pathological unbroken delta run beyond the scan
  cap fails closed with `session_history_scan_limit` instead of silently
  dropping content.
- New `run.subscribe` command (`RunSubscribeParams` / `RunSubscribedResult`):
  a second App Protocol connection can follow a run started by another
  connection. The runtime keeps a per-run owner map and a per-run subscriber
  map keyed by connection id, and `publish_to_subscribers` fans each durable
  event out to every subscriber except the owner (which already receives it
  through its run sink). Fan-out is invoked from the run sink, `session.steer`,
  `run.cancel`, `approval.resolve`, the approval gate and the owner-disconnect
  cancellation, and always uses the already-masked, already-persisted envelope,
  so it cannot bypass secret masking or the frame-size guard. Subscribers are
  removed on terminal and on disconnect; a run that terminates between the
  status read and registration is detected by a post-registration re-read and
  reported `terminal`, so the client is never left waiting.
- Capabilities `run_subscribe`, `session_history_cursor` added; the typed SDK
  gained `runSubscribe`, `sessionHistoryPage`, `promptWith` and the generated
  `Command` union grew to 148 commands.
- Generated artifacts regenerated from the Rust types: JSON Schema and both
  `cool_protocol.ts` copies.

### Increment 4 — React chat cutover

- `frontend/src/api/sdk.ts` is the single typed boundary to the facade: one
  `HttpTransport` (same-origin by default, `VITE_COOL_API_URL` override,
  `VITE_COOL_API_TOKEN` bearer, credentials `same-origin` so the browser
  `cool_client` cookie carries identity) and the `CoolSdk` built on it. The
  generated SDK sources are resolved through the `@cool-sdk` Vite alias and
  tsconfig path, so the SPA and the coverage gate share the exact generated
  types.
- `frontend/src/api/mappers.ts` (new, excluded from the operation inventory like
  `client.ts`) converts generated camelCase records into the snake_case view
  types the pages already consume.
- `conversationsApi` is cut over: `list/create/update/delete/compact` now map to
  the typed commands (breakpoints travel in `metadata`), `listApprovals` maps
  `conversations.approvals`, `approveToolCall` resolves the live run through
  `approval.resolve` (durable, `approvalId` + `expectedRevision`), and the new
  `listRuns` reads `session.runs`. `get` composes the legacy metadata record
  with the canonical transcript: `session.for_conversation` (find-or-create the
  durable session and one-time import) followed by paginated `session.history`
  reads up to a bounded 100x100 window. The `session.for_conversation`
  idempotency key is stable per conversation so polling reads replay the durable
  link instead of re-projecting the legacy transcript.
- `streamConversationMessage` drives a canonical turn (text only):
  `session.for_conversation` -> `session.prompt` (`planMode`/`systemPrompt`) ->
  `streamRunEvents` on the canonical cursor/reconnect SSE. The token is
  forwarded to the stream via `Authorization` (never the URL). A legacy
  `POST /api/conversations/{id}/messages` SSE fallback remains only for sends
  that carry `artifact_ids`, because `session.prompt` still rejects non-text
  `ContentPart`s; it projects the legacy events into canonical envelopes so the
  hook has one reducer.
- `useConversationStream` consumes canonical `EventEnvelope`s: content/reasoning
  deltas, tool requested/started/completed/failed, usage, plan events,
  subagents, budgets, approvals. `respondApproval` calls `approval.resolve` with
  the event's `approvalId`/`revision`; `cancel` aborts the stream *and* issues
  `run.cancel`. The optimistic user/assistant view-model, rAF throttling, and
  inline approval card are unchanged.
- Rust `HistoryItem` gained `cursor`, `occurredAt`, `runId`, `model` and
  `usage`, and `PlanCreated` gained the full `steps` list (both additive at v1,
  `steps` `serde(default)`), so the canonical transcript can render persisted
  history without the legacy tables.
- History pagination hardening: an assistant `ItemCompleted` is now treated as
  group-internal (its leading reasoning may still be older), and `usage.updated`
  is no longer a page boundary, so a reasoning group can never be split across
  pages or attached to the wrong item. Per-run models are resolved for
  page-contained runs or with one bounded `store.events(.., 1)` read for a run
  whose `run.started` is older than the page. `pending_usage` is reset on every
  run boundary so one run's usage cannot attach to the next run's assistant item.
- `frontend/protocol-tests/inventory.json`: `conversations.approveToolCall`
  moved from `deferred` to `sdk` (`approval.resolve`), `conversations.listRuns`
  added (`session.runs`), and the `streamConversationMessage` rationale now
  records the canonical path and the attachment fallback.

## Compatibility

- The App Protocol v1 surface, generated schema, golden traces, SDK method
  names and `plugins.lock.json` are unchanged; the facade only projects the
  existing protocol over HTTP/SSE.
- No Python or frontend runtime behavior changed: the FastAPI REST/WS backend
  is still the running production path until the React cutover lands. This
  increment is additive and opt-in via `cool serve`.
- Increment 2 is additive at App Protocol v1: three new commands
  (`session.for_conversation`, `session.runs`, `conversations.messages`) and
  the new capabilities `conversation_sessions`/`session_runs`. No existing
  command, event, golden trace or record shape changed; the generated schema
  and both TS copies are regenerated from the Rust types without manual wire
  types. The legacy `conversations`/`messages` tables stay untouched and the
  Rust session/link state lives in `rust-core.db`; until the frontend is
  switched, the Python runtime remains the only chat writer.
- `rust_runs.finish_reason` was previously never written; it is now populated
  from terminal events. This is additive and not consumed by any other client
  yet.
- Increment 3 is additive at App Protocol v1: two optional prompt params
  (`planMode`, `systemPrompt`), one optional history param (`beforeCursor`) and
  one new result field (`nextCursor`), plus the new `run.subscribe` command and
  the `run_subscribe`/`session_history_cursor` capabilities. No existing field
  was removed; `hasMore`/`items` are retained. A strict older v1 client that
  uses `deny_unknown_fields` on *results* would reject `nextCursor`, which is
  the normal versioned-peer caveat the strict golden test already treats as out
  of contract. The legacy `conversations`/`messages` tables stay untouched and
  the Python runtime remains the only chat writer until the React cutover.

Increment 4 is additive at App Protocol v1: five new `HistoryItem` fields and an
optional `PlanCreated.steps` list. No existing field, command, golden trace or
record shape changed; the schema and both TS copies are regenerated from the
Rust types. The strict older-v1 caveat still applies (`deny_unknown_fields` on a
result struct rejects the new fields), which the golden test treats as out of
contract. The legacy `conversations`/`messages` tables stay read-only from Rust;
the frontend now reads the canonical transcript for chat, and reaches the Python
runtime only through the attachment fallback until non-text `ContentPart`s are
supported. Other React subsystems still use the Python REST/WS clients.

## Data and security

- The HTTP facade never opens SQLite directly: commands go through the same
  actor-scoped `AppServer` dispatch as other transports.
- Fail-closed ordering: profile validation happens before binding, so a
  misconfigured `server` deployment cannot start; request bodies are capped at
  the 1 MiB protocol frame limit; `local` refuses non-loopback peers, opaque
  origins, and cross-origin reads as well as mutations; `server` requires an
  exact Origin whenever one is present and a mandatory Origin on mutations.
- The connection-pool cap (`503` when full) bounds the resource cost of forged
  client identities; identity creation no longer serializes all clients behind
  one handshake, and an unauthenticated request that would mint a new identity
  is refused on the SSE endpoint (`403 client_identity_required`) unless a
  token is configured. A browser without the `cool_client` cookie cannot open
  a stream at all, which closes the cross-site no-cors GET path.
- No new secrets are logged or returned; `ServerConfig`'s secret-presence-only
  `Debug` is unchanged. No `unsafe` code (workspace forbids it).

Increment 2:

- One-way projection, no dual write: `session.for_conversation` reads the
  legacy store but writes only `rust_*` tables. The canonical session is the
  only place new turns will be recorded after the frontend cutover; the legacy
  `messages` table is never modified by the Rust runtime.
- Identity: the command carries no actor field; the actor is derived by the
  server (`local_actor()` today, transport identity is an M11/M12 follow-up),
  and the link table + run listing reject a foreign actor with
  `ActorMismatch`. `deny_unknown_fields` on all three param types keeps payload
  fields from smuggling identity.
- Idempotency: same actor+key replays the stored `ConversationLink`; a changed
  fingerprint raises `idempotency_conflict`; a different key on an existing
  link returns `created=false` with no second import. Concurrency is proven
  across four separate SQLite connections (exactly one creator, one import
  run).
- Secrets: imported event content goes through `masked_envelope`, and
  `rust_runs.finish_reason` is now derived from the masked envelope as well.
  Imported `occurred_at` values are parsed with a year bound (1..=9999) so
  crafted timestamps cannot overflow the civil-date math.
- Bounds: the import window is capped at 10 000 newest messages by a single
  indexed query and reports `truncated`; `conversations.messages` rejects
  out-of-range limits; `session.runs` is bounded by the negotiated
  `event_page_limit`. Oversized RPC frames still fail closed.
- Data ownership: SCHEMA_VERSION 1 -> 2 is additive (`rust_conversation_links`
  + index); a v1 database upgrades in place with sessions/runs/events intact
  and a newer-than-supported version still fails closed.

Increment 3:

- Identity stays actor-scoped: `run.subscribe` and `session.history` read the
  run/session through `local_actor()` and the store re-checks ownership
  (`ActorMismatch`), so a subscriber can only follow a run it already owns; the
  subscriber map is keyed by run id, which is safe while the local facade is
  single-actor (the `server` profile's multi-actor work must revisit this).
- Fan-out cannot bypass masking or frame limits: subscribers receive the
  already-masked, already-persisted `EventEnvelope` that the run sink produced
  after `mask_canonical_event` and `preview_event_frame_fits`, and only the
  owner-send path was reordered (fan-out now happens before the owner send) so
  a failed owner delivery cannot withhold a terminal from subscribers.
- Planning mode is fail-closed: the caller's `systemPrompt` is dropped and the
  runtime directive is used, so a caller cannot steer plan generation. The
  prompt is used only for the model request and is never persisted.
- Pagination is bounded and group-safe: `session_event_window` reads
  `limit + 1` rows per chunk on the append-only `rust_events.rowid`; the
  history read walks until the window starts at a non-delta event, and a
  pathological unbroken delta run beyond the scan cap fails closed with
  `session_history_scan_limit` rather than dropping content.
- `rust_events` rows are append-only and never deleted or vacuumed by the
  runtime (no `DELETE FROM rust_events`/`VACUUM`), so the rowid cursor is
  stable for the lifetime of the store; a future compaction would need to
  switch the cursor to `event_id`.
- No new secrets are logged; the caller system prompt is never written to
  events. No `unsafe` code.

Increment 4:

- The frontend boundary is the canonical protocol only: every translated chat
  operation goes through `AppServer` dispatch (same actor scoping and store
  rules as the stdio/TUI/ACP transports), and the browser identity is the
  HttpOnly `cool_client` cookie; `HttpTransport` uses `credentials:
  "same-origin"` and no command payload carries identity.
- The bearer token (when configured) is sent to both `POST /api/rpc` and
  `GET /api/events` via `Authorization`, never the URL. Tokens passed through
  `VITE_COOL_API_TOKEN` are compiled into the SPA bundle, so the `server`
  profile must serve that bundle behind its own auth boundary.
- The transcript read is bounded: `session.for_conversation` uses a stable
  per-conversation idempotency key so repeated/polling reads replay the durable
  link rather than re-projecting up to 10 000 legacy messages; `session.history`
  is bounded by the negotiated page limit, and the per-run model lookup is a
  single bounded first-event read per run that cannot outlive its `run.started`.
- History projection cannot leak usage across runs (`pending_usage` resets on
  every run boundary) and cannot split a reasoning group across pages (assistant
  items and `usage.updated` are group-internal boundaries).
- No new secrets are logged or persisted; the attachment fallback is the only
  path that still talks to the Python runtime, and it carries no new identity.

## Residual risks

- Each distinct `cool_client` identity holds a live protocol connection for
  the process lifetime. The pool is bounded at 128 and refuses new identities
  when full, but there is no idle eviction yet: a legitimate long-lived
  deployment with many browsers would need eviction with run-safety analysis,
  and (accepted) a local caller can occupy all 128 tokenless-local slots for
  the process lifetime. That caller can be a co-located process (which already
  has filesystem access) or, because `localhost` is itself a loopback origin,
  a *different local web app* (`http://localhost:3000`) whose `POST /api/rpc`
  mints identities. Non-loopback/opaque origins and anonymous SSE are refused,
  so this is not remotely reachable; it is the accepted cost of a tokenless
  single-user local default.
- The SSE stream cannot know locally that a run is already terminal when the
  requested cursor is already past the terminal seq, so it stays live and
  emits keepalives instead of a synthetic terminal frame. Clients that know
  the run finished should close the stream.
- `?token=` auth for `EventSource` places the token in the URL (and thus
  access logs); the `Secure` cookie path is preferred where a login flow can
  set it. Recorded here because the server profile currently has no login flow.

Increment 2:

- A legacy tool row whose result matches no pending assistant call (corrupt or
  hand-edited store) is still projected as a standalone tool role; matched
  results are normalized, and leading orphans are trimmed, so only
  mid-transcript corruption can produce it.
- The import window is bounded at 10 000 newest messages; the truncation path
  itself is implemented and reported via `truncated`, but no integration test
  seeds more than 10 000 messages (the `recent_messages` boundary logic is unit
  tested instead).
- A rebind with a new idempotency key reports `created=false`,
  `imported_events=0` and the *current read's* `truncated` flag, so
  `truncated=true` with `created=false` is a valid response.
- Imported `occurred_at` keeps whole-second precision (`.000Z`); durable order
  comes from run/seq, not the timestamp.
- The oversized-frame test now configures 1024 bytes because the initialize
  response grew with the two new capabilities; a much larger capability list
  would require the test limit (or the handshake budget) to be revisited.
- The import read/projection runs synchronously on the async dispatcher, like
  the rest of the legacy family dispatch; one very large source conversation
  can stall the connection task while it works (bounded to one indexed window
  query plus mapping).
- `parse_python_datetime` now rejects years outside 1..=9999, but the public
  `days_from_civil` helper itself still uses unchecked arithmetic; all current
  callers pass bounded values (latent API hazard only).

Increment 3:

- The history cursor is `rust_events.rowid`. The runtime never deletes or
  vacuums events, so it is stable today; any future store compaction must move
  the cursor to `event_id` before it renumbers rows.
- `session.history` is newest-first pages; the walk stops at a non-delta group
  boundary, so a page whose oldest group exceeds the scan cap fails closed
  (`session_history_scan_limit`) rather than returning partial reasoning. A
  legitimate turn with an enormous reasoning stream could therefore be
  unreadable through this command until the client lowers `limit` (which raises
  the cap proportionally).
- Fan-out is sequential and awaits each subscriber's bounded send, so one slow
  subscriber can briefly delay the owner's run sink and other subscribers; the
  subscriber map is keyed by run id and assumes a single actor, which is safe
  for the local facade but must be revisited when the `server` profile
  introduces multiple actors.
- The HTTP/SSE facade does not call `run.subscribe`; the SDK comment describes
  the command, but no `cool-http` integration test yet proves a browser on a
  second identity can follow a foreign run through the facade (the app-server
  tests prove the protocol-level fan-out).
- The fan-out test holds a run with a gated tool; the disconnect-cancel
  terminal fan-out test uses a long provider delay. Both are deterministic
  under normal load but the disconnect test still depends on cancellation
  racing the delayed provider.
- `bounded_history` could in principle return `has_more=true` with no
  `next_cursor` if a bounded window projected to zero items; the walk only
  stops at a group boundary that always projects to an item, so this is
  unreachable today, but a client should treat a missing cursor as terminal.
- The approval-request fan-out in the approval gate publishes before the owner
  send, so a subscriber sees `tool.approval_required` even if the owner has
  disconnected; the waiter still fails the run closed when the owner cannot be
  reached, so the run does not hang.

Increment 4:

- The canonical transcript read caps at 100 pages x 100 items (10 000 items);
  older history past that bound is not shown through `conversationsApi.get` and
  the client has no truncation signal (the import itself is bounded server-side
  and reports `truncated`).
- `session.history` resolves the `model` for each distinct run on a page with
  one bounded `store.events(.., 1)` read when the run's `run.started` is older
  than the window; a page spanning many runs issues that many small queries.
- `PlanCreated.steps` is `serde(default)` on the wire but the generated TS marks
  it required (ts-rs ignores `serde(default)`), so the reducer guards with
  `?? []`; a Python producer that omits `steps` is handled. ACP's plan
  projection still assumes 1-based positions while the runtime emits 0-based
  (pre-existing, not introduced here).
- Plan status values are a loose string on the wire; a runtime `status` outside
  the frontend `PlanStepStatus` union renders with the generic fallback icon.
- `VITE_COOL_API_TOKEN` is compiled into the public SPA bundle; the `server`
  profile must serve that bundle behind its own authentication.
- The reducer does not enforce the canonical `seq` (the replay helper
  `canonicalReducer.ts` does); duplicate/late events are tolerated rather than
  rejected, which is safe because `streamRunEvents` reconnects on the durable
  cursor.
- The legacy attachment fallback remains on the Python SSE path; it is degraded
  (no canonical durability, fake `seq: 0`, Python-only) and only usable where
  the Python backend is reachable.
