# M11 checkpoint — Web cutover and compatibility workers

Status: **in progress (partial)**. The Rust HTTP/App Protocol facade and the
`cool serve` entrypoint are implemented and covered by tests, and the chat
cutover foundations (conversation -> session binding with canonical transcript
import, run listing, paginated legacy transcript reads) plus the canonical
prompt inputs, durable history cursor and live-run fan-out are implemented on
the Rust side. The React **chat** surface is now switched onto the generated
`CoolSdk`/`HttpTransport` boundary (`conversations`, canonical
`session.prompt` + `streamRunEvents`, `approval.resolve`), and `session.history`
was enriched so the persisted transcript can render without the legacy
`messages` table. Every store-backed React API subsystem is now on the SDK
(Increment 5), two canonical runtime catalog commands (`tools.list`,
`tasks.templates`) landed (Increment 6), and the canonical task records now
derive their schedule fields with the built-in template catalog expanded
server-side (Increment 7), and the background task scheduler/executor
(Increment 9), the foreground **subagent executor** (Increment 10), canonical
**webhook replay** (Increment 11), canonical **plan execution** (Increment 12)
and canonical **conversation compaction** (Increment 13) now run through the
Rust runtime. The live-stream canonicalization has landed on the Rust side
(Increment 14: the HTTP/SSE facade calls `run.subscribe`, subagent child
streaming stays poll-based and research is explicitly re-scoped as deferred, see
Deferred Group A) and the experimental OpenCode Bun compatibility worker landed
(Increment 15: opt-in, isolated, Bun-free CI tests) and the single-binary Rust
packaging/upgrade path landed (Increment 16: Rust multi-stage image, explicit
`cool store adopt` with verified backup, upgrade/rollback test). The remaining
execution engine (research), the M8 extension/network admin surfaces
(`mcp.*`, `skills.*`, `providers.previewModels`, `memory.extract`,
`rss.fetchNow`, settings), the optional Python workers, the worker permission
review/status web UI and the `server`-profile operationalization / Python
retirement (M12) are **not** done, so the phase stays `[~]` and must not be
treated as complete.

## Implemented

- New crate `crates/cool-http` (M11 §"Web cutover"):
  - `HttpFacade` wraps the existing `AppServer` without owning any agent,
    store or policy logic. Each browser identity is one in-process App
    Protocol connection: `AppServer::serve_io` runs over a `tokio::io::duplex`
    pipe and is driven by the existing `AppClient` (`ConnectionPool`), so the
    HTTP layer sees exactly the stdio/TUI/ACP request/response and live-event
    semantics. Connection creation runs outside the pool lock; the pool is
    capped at 128 live identities and refuses new ones with `503` instead of
    evicting a connection that could own a run.
  - `GET /api/health` — public liveness/phase/capabilities document.
  - `POST /api/rpc` — accepts the canonical `RpcRequest` and returns the
    canonical `ServerFrame` (`RpcSuccess`/`RpcFailure`) with the request id
    echoed, so no HTTP-specific business model is introduced. Only a parse
    failure or an unavailable protocol connection uses a small structured
    transport error; command errors stay canonical `RpcFailure`.
  - `GET /api/events?runId&afterSeq&limit` — SSE stream with canonical
    cursor/reconnect semantics: subscribe → durable catch-up via `run.events`
    → live tail filtered by `seq`, re-catch-up on `Lagged`, `Last-Event-ID`
    precedence over `afterSeq`, and `end` on terminal. Payloads are
    re-projected (a bare `EventEnvelope` for `run.event`, the protocol
    `StreamKeepalive`/`StreamEnd` payloads for keepalive/end), not the tagged
    `StreamFrame` enum. `limit` is clamped to the server-configured
    `event_page_limit` so the facade never requests a page the runtime rejects.
    A client that reconnects with a past cursor cannot double-apply an event.
    An unauthenticated request that would mint a brand-new identity is refused
    (`403 client_identity_required`) unless a token is configured, so a
    cross-site no-cors GET (no Origin, no SameSite cookie) cannot spawn
    connections.
  - Production React assets are served from `--assets` with an SPA
    `index.html` fallback (tower-http `ServeDir::fallback`); without assets
    the root returns a diagnostic placeholder.
- Deployment profiles (`crates/cool-http/src/auth.rs`), fail-closed at startup:
  - `local` (default): loopback-only peer enforcement, optional shared token,
    loopback Origin allowlist that is enforced whenever an Origin is present
    (reads and mutations), non-loopback bind refused without `--allow-remote`
    **and** a token. A present-but-unparseable Origin (`null`, empty, opaque)
    and duplicate `Origin` headers are rejected rather than treated as "no
    Origin"; IPv6 loopback origins (`http://[::1]:…`) are accepted.
  - `server`: token mandatory, `--tls-terminated`/`--trusted-proxy` boundary
    mandatory, `--public-url` mandatory, exact-Origin enforcement whenever an
    Origin is present plus a required Origin on mutations, `Secure` client
    cookie.
  - Token auth accepts `Authorization: Bearer`, `?token=` (for native
    `EventSource`) and a cookie, compared in constant time; client identities
    are generated, validated, and persisted in an HttpOnly `SameSite=Strict`
    `cool_client` cookie. A valid `x-cool-client` header wins, but an invalid
    header no longer shadows a valid cookie.
- `cool serve` CLI command (`crates/cool-cli`): `--data-dir`, `--bind`,
  `--port`, `--assets`, `--profile`, `--token`, `--public-url`,
  `--trusted-proxy`, `--tls-terminated`, `--allow-remote`, `--legacy-store`;
  reuses `build_server` so `--legacy-store` serves the typed legacy families.
  `cool doctor` now reports `phase: M11`, `webFacade`,
  `serveProfiles: ["local","server"]`.
- `sdk/typescript/src/http.ts`: `HttpTransport` (commands over `POST /api/rpc`)
  and `streamRunEvents` (async SSE iterator) implementing the existing
  `CoolTransport` contract. Both send the token via `Authorization`, never
  `?token=`, and the header documents that Node callers must reuse one
  `clientId` across a transport and its event stream. Typechecked by
  `npm run protocol:check`.

### Increment 2 — chat cutover foundations (Rust side)

- `session.for_conversation` (`crates/cool-protocol/src/lib.rs`): find-or-create
  the durable Rust session bound to one legacy conversation. The first call
  creates `rust_conversation_links(conversation_id, actor_id, session_id)` in
  `rust-core.db` (SCHEMA_VERSION 1 -> 2, additive) and an import run that
  projects the legacy transcript into the canonical event log
  (`run.started` mode `import` -> items/tool results -> `run.completed` reason
  `import`). No legacy table is written: this is a one-way projection, not a
  dual write. Replays answer from the durable idempotency record before the
  legacy store is touched, so repeating the command is cheap and still returns
  the original result after the source conversation was deleted. A link owned
  by another actor fails closed (`ActorMismatch` -> `resource_not_found`).
- History projection (`crates/cool-app-server/src/lib.rs`): user/assistant
  rows become `item.completed` (assistant `thinking` becomes `reasoning.delta`
  first), assistant `tool_calls` become `ToolRequested`s, tool rows become
  `tool.completed` or `tool.failed` (`is_error`), and assistant calls without a
  persisted result are backfilled as `tool.failed` (`legacy_tool_unanswered`),
  mirroring the Python `_backfill_missing_tool_results` so the imported history
  is a provider-valid transcript. Result rows match pending calls by stored
  id, then by a unique name, then by the only pending call; missing names/ids
  degrade to stable synthetic values instead of dropping rows. Legacy
  timestamps are normalized to RFC3339. Structurally invalid JSON in a legacy
  column still fails the read closed (strict store parsing).
- Bounded reads: `crates/cool-store` adds `RecentMessages`
  (`LegacyStore::recent_messages`) — one `ORDER BY id DESC LIMIT limit+1` query
  returning the newest window oldest-first plus `has_more`, bounded at
  10 000 rows — so linking never scans a whole transcript. `session.runs`
  lists durable runs of one actor-owned session newest-first (bounded by
  `event_page_limit`). `conversations.messages` is a paginated legacy
  transcript read (`before_id`, limit 1..=2000; out-of-range limits are
  rejected). Leading orphan tool rows are trimmed from the import window and
  `SessionConversationResult.truncated` reports that the projection is not the
  complete transcript.
- `rust_runs.finish_reason` is now populated for terminal events, derived from
  the *masked* envelope so a secret in a terminal/cancel reason cannot outlive
  the event log in run summaries.
- Generated artifacts regenerated from the Rust types: JSON Schema, both
  `cool_protocol.ts` copies, and the typed SDK gained
  `sessionForConversation`, `sessionRuns`, `conversationsMessages`.

### Increment 3 — canonical prompt inputs, history cursor, run fan-out

- `session.prompt` params gained `planMode` and `systemPrompt`
  (`crates/cool-protocol/src/lib.rs`). `AgentRequest` gained a `mode` field
  (`crates/cool-agent/src/loop_runtime.rs`) that is surfaced on `run.started`.
  In planning mode the app-server shadows any caller `systemPrompt` with the
  runtime-owned `PLANNING_SYSTEM_PROMPT` (`crates/cool-agent/src/context.rs`)
  and marks the run mode `plan`; the trusted `update_plan` tool still projects
  `plan.created` / `plan.step_*` events, so planning is provider-driven rather
  than a Python-only code path. Non-planning turns forward the caller system
  prompt; the prompt is used only for the model request and never persisted.
- `session.history` gained durable pagination: params carry `beforeCursor`
  (exclusive) and the result carries `nextCursor`/`hasMore`
  (`crates/cool-protocol/src/lib.rs`). The new
  `DurableStore::session_event_window` (`crates/cool-state/src/lib.rs`) pages
  on the append-only `rust_events.rowid` newest-first with `limit + 1` rows, so
  the read is bounded and never scans the whole log. `session_history` walks
  event chunks until the window begins at a history-group boundary (an
  item/tool event, never a `content.delta`/`reasoning.delta`), so a run of
  deltas is never split from the item it belongs to and `nextCursor` always
  points at a group start. A pathological unbroken delta run beyond the scan
  cap fails closed with `session_history_scan_limit` instead of silently
  dropping content.
- New `run.subscribe` command (`RunSubscribeParams` / `RunSubscribedResult`):
  a second App Protocol connection can follow a run started by another
  connection. The runtime keeps a per-run owner map and a per-run subscriber
  map keyed by connection id, and `publish_to_subscribers` fans each durable
  event out to every subscriber except the owner (which already receives it
  through its run sink). Fan-out is invoked from the run sink, `session.steer`,
  `run.cancel`, `approval.resolve`, the approval gate and the owner-disconnect
  cancellation, and always uses the already-masked, already-persisted envelope,
  so it cannot bypass secret masking or the frame-size guard. Subscribers are
  removed on terminal and on disconnect; a run that terminates between the
  status read and registration is detected by a post-registration re-read and
  reported `terminal`, so the client is never left waiting.
- Capabilities `run_subscribe`, `session_history_cursor` added; the typed SDK
  gained `runSubscribe`, `sessionHistoryPage`, `promptWith` and the generated
  `Command` union grew to 148 commands.
- Generated artifacts regenerated from the Rust types: JSON Schema and both
  `cool_protocol.ts` copies.

### Increment 4 — React chat cutover

- `frontend/src/api/sdk.ts` is the single typed boundary to the facade: one
  `HttpTransport` (same-origin by default, `VITE_COOL_API_URL` override,
  `VITE_COOL_API_TOKEN` bearer, credentials `same-origin` so the browser
  `cool_client` cookie carries identity) and the `CoolSdk` built on it. The
  generated SDK sources are resolved through the `@cool-sdk` Vite alias and
  tsconfig path, so the SPA and the coverage gate share the exact generated
  types.
- `frontend/src/api/mappers.ts` (new, excluded from the operation inventory like
  `client.ts`) converts generated camelCase records into the snake_case view
  types the pages already consume.
- `conversationsApi` is cut over: `list/create/update/delete/compact` now map to
  the typed commands (breakpoints travel in `metadata`), `listApprovals` maps
  `conversations.approvals`, `approveToolCall` resolves the live run through
  `approval.resolve` (durable, `approvalId` + `expectedRevision`), and the new
  `listRuns` reads `session.runs`. `get` composes the legacy metadata record
  with the canonical transcript: `session.for_conversation` (find-or-create the
  durable session and one-time import) followed by paginated `session.history`
  reads up to a bounded 100x100 window. The `session.for_conversation`
  idempotency key is stable per conversation so polling reads replay the durable
  link instead of re-projecting the legacy transcript.
- `streamConversationMessage` drives a canonical turn (text only):
  `session.for_conversation` -> `session.prompt` (`planMode`/`systemPrompt`) ->
  `streamRunEvents` on the canonical cursor/reconnect SSE. The token is
  forwarded to the stream via `Authorization` (never the URL). A legacy
  `POST /api/conversations/{id}/messages` SSE fallback remains only for sends
  that carry `artifact_ids`, because `session.prompt` still rejects non-text
  `ContentPart`s; it projects the legacy events into canonical envelopes so the
  hook has one reducer.
- `useConversationStream` consumes canonical `EventEnvelope`s: content/reasoning
  deltas, tool requested/started/completed/failed, usage, plan events,
  subagents, budgets, approvals. `respondApproval` calls `approval.resolve` with
  the event's `approvalId`/`revision`; `cancel` aborts the stream *and* issues
  `run.cancel`. The optimistic user/assistant view-model, rAF throttling, and
  inline approval card are unchanged.
- Rust `HistoryItem` gained `cursor`, `occurredAt`, `runId`, `model` and
  `usage`, and `PlanCreated` gained the full `steps` list (both additive at v1,
  `steps` `serde(default)`), so the canonical transcript can render persisted
  history without the legacy tables.
- History pagination hardening: an assistant `ItemCompleted` is now treated as
  group-internal (its leading reasoning may still be older), and `usage.updated`
  is no longer a page boundary, so a reasoning group can never be split across
  pages or attached to the wrong item. Per-run models are resolved for
  page-contained runs or with one bounded `store.events(.., 1)` read for a run
  whose `run.started` is older than the page. `pending_usage` is reset on every
  run boundary so one run's usage cannot attach to the next run's assistant item.
- `frontend/protocol-tests/inventory.json`: `conversations.approveToolCall`
  moved from `deferred` to `sdk` (`approval.resolve`), `conversations.listRuns`
  added (`session.runs`), and the `streamConversationMessage` rationale now
  records the canonical path and the attachment fallback.

  (not the legacy family) so they work without `--legacy-store`:

### Increment 9 — Rust task scheduler/executor

- New `crates/cool-app-server/src/scheduler.rs` (`TaskExecutor`) wires the
  deterministic `cool-store::scheduler` engine to the Rust agent runtime:
  - `tick(now)` plans due tasks (`Scheduler::plan`), records skips as durable
    skipped runs, and spawns an execution for each `Execute` decision;
    `run_now` triggers a manual run; `cancel` signals the live run's cancel
    channel and flips the row; `status` reports the real engine
    (`running=true`, enabled jobs with their `next_run_at`); `spawn_loop`
    drives a periodic tick.
  - Executions run through `AgentRuntime` with the task's model, iteration
    limit, cost cap, timeout, tool whitelist and working directory. The task's
    stored `capability_policy` is applied as a narrowing child policy (a task
    can only restrict, never widen, the core policy) and a `deny_external` task
    additionally denies `send_external`; other approval-gated tools are
    auto-approved, matching Python's background-run semantics. An unusable
    working directory fails the run closed instead of falling back to the
    server workspace. The terminal assistant text (secret-masked), usage,
    duration and status are written to the durable `task_runs` row via
    `finish_task_run` + `record_task_outcome`; a cancel does not count as a
    failure.
- `cool-store`: `Scheduler::mark_running` added; `SchedulerConfig` is now
  `Copy`.
- App server: `Inner.task_executor` is built whenever a legacy store is
  configured; `AppServer::task_executor()` exposes it; `tasks.run`,
  `tasks.runs_cancel` and `tasks.scheduler` are dispatched by the executor
  (falling back to `legacy_store_unavailable` without a store) and the old
  store-only arms were removed from `legacy/admin.rs`.
- `cool-cli::build_server` starts the executor loop (15 s interval) so
  `cool serve`/`app-server` actually schedule tasks.
- Frontend: `tasksApi.runNow`/`cancelRun`/`scheduler` cut over to
  `sdk.tasksRun`/`tasksRunsCancel`/`tasksScheduler`; new `toSchedulerStatus`
  mapper. Inventory: **124 sdk operations across 150 commands**, exceptions
  `{deferred:30, static/blob:4, sse/stream:4}`.

### Increment 10 — Rust subagent executor

- New `crates/cool-app-server/src/subagents.rs` (`SubagentExecutor`) drives
  `subagents.launch`, `subagents.launch_batch` and `subagents.runs_cancel`
  through `AgentRuntime::run_subagent` instead of only writing rows:
  - `launch` resolves role/profile configuration with the Python precedence
    (model override > profile > role > default; system prompt profile > role;
    tool names profile > role > all; `max_iterations`/`max_cost_usd` from the
    role), creates the isolated child conversation, a queued child `agent_runs`
    row, the prompt as the child's first user message, and the `subagent_runs`
    row linking `run_id`; then spawns execution. A role/profile capability
    policy is applied as a **narrowing** child of the core policy (like
    `TaskExecutor::task_policy`).
  - The child transcript is projected into the legacy `messages` table (user
    prompt + assistant items with tool calls/thinking/usage + tool rows) so the
    React `subagents.runs_get` transcript works; the terminal assistant text is
    the `result_summary`. This is the **documented subagent exception** to the
    single-writer rule (see Data and security).
  - Subagent lifecycle is projected into the parent conversation's canonical
    session when it is linked: an auxiliary run (`DurableStore::start_auxiliary_run`,
    which never becomes the session's active run) carries
    `subagent.started/completed/failed` and a terminal `run.completed/failed/
    cancelled`. An unlinked parent degrades to a no-op sink (residual).
  - `cancel` authorizes the run, signals the live cancel channel and flips a
    non-terminal row; a terminal run is returned unchanged (Python parity).
    Finalization uses `finalize_subagent_run`, which preserves a cancellation
    that landed while the executor was finishing.
  - The live cancel map is a `std::sync::Mutex` guarded by a `Drop` guard, so a
    panic in the executor task cannot leak an entry.

### Increment 12 — canonical plan execution

- New `plans.execute` command (`IdempotentPlanIdParams` -> `PlanExecuteResult`,
  capability `plan_execution`). It requires an `approved` plan, transitions it

  spawns the step loop. It is idempotent on `(actor, key)` through the run's

### Increment 14 — live-stream canonicalization (WS3)

- **Facade `run.subscribe`.** `crates/cool-http`'s SSE stream now opens with a
  canonical `run.subscribe` on the browser's own App Protocol connection before
  replaying the durable backlog (`routes.rs::Phase::Subscribe`). A browser on a

  `POST /api/research/stream` and `research.create`/`cancel`/`rerun` remain on

### Increment 15 — OpenCode Bun compatibility worker (WS1)

- `CompatibilityAdapter::OpenCode` (experimental) joins Codex/Claude on the same
  versioned worker RPC (`opencode.request`, capability `opencode_protocol`,
  response field `result`); `is_executable()` marks the adapter that hosts
  vendor code. The handshake/deadline/cancel/heartbeat/shutdown/structured-error
  and restart/`UnknownOutcome` semantics are unchanged.
- New `crates/cool-extensions/src/opencode.rs` (`opencode_launch_spec`,
  `opencode_worker_policy`):
  - The launcher validates the immutable install root and the writable data
    root (both dirs, no symlink/reparse point, non-overlapping), the entry
    (inside the root, regular file, not link-like, allowed JS/TS extension) and
    the granted workspaces (existing dirs, canonicalized, deduplicated).
  - It spawns the configured Bun program with a fixed `run <entry>` argument
    vector and a working directory inside the writable data root (never the

    onto a narrowing child of the core policy (an undeclared capability is

  function. A missing Bun, an invalid tree or a denied capability is reported as

  operator-provided entry: it applies the same launcher-level checks (real
  non-link, non-overlapping install/data roots; entry inside the install root;

  stays a store operation. A committed corpus at
  `crates/cool-extensions/tests/fixtures/opencode-plugin/` (`plugin.json` +
  `lib/index.ts` + `package.json`) records version and dependency metadata.
- Worker status is surfaced through the existing `ExtensionRuntime::status_events`

- Tests stay Bun-free: the versioned protocol, request/response translation,
  crash isolation with no side-effect replay, an unstarted adapter, secret-env
  stripping, the launch-spec isolation/capability mapping and the status
  surface are all driven by the existing stub helper binary; the real Bun worker

  failing the turn. The CLI installs `FileAppSettings` in `build_server`.

### Increment 21 — tool-registry parity audit and staged plan (WS2a, no code)

Decision (recorded with the user): expand the Rust registry toward parity rather
than annotate `tools.list` with an executor/source. This increment is the audit
and the staged plan; no code changed, so no gates were re-run.

**Authoritative inventories.** Python has **65 static tools** registered in
`backend/app/tools/*` + `backend/app/memory/tools.py` (`register_builtins`), plus
dynamic `macro_*` tools (`app/agent/constructor.py`) and MCP bridge tools
(`app/mcp/tool_bridge.py`). Rust has **6 builtins** in
`crates/cool-agent/src/tools.rs::builtin_registry` (`read_file`, `list_files`,
`write_file`, `shell`, `git`, `update_plan`) plus MCP plugin tools merged by the
CLI (`extension_registry`). The Rust registry is built by the CLI and reaches the
catalog through `AppServer::tool_catalog()`, so expanding it needs no protocol
change (the catalog already projects whatever the runtime registers).

**Who executes a `tool_names` entry today.** Subagent roles/profiles and
scheduled tasks execute in Rust against the 6+MCP registry (an unknown name is
silently dropped). Profile chat turns, agent-constructor macros, and every other
family still execute in Python. Therefore the pickers cannot be cut over until
the Rust registry covers each name a Rust-executed config may reference.

**Feasible local families (no network/ML/Python needed), in staged order.**

1. **Store-backed memory** (`memory_remember`, `memory_recall`, `memory_forget`,
   `memory_update`, `memory_list`, `set_working_memory`, `get_working_memory`,
   `entity_lookup`): `cool-store` already has `create/list/update/delete/get/pin`
   memory items, working-memory upsert/get and `list_entities` with substring
   match. Blocker: `ToolContext` carries no actor/conversation, and working memory
   and conversation scope need both. First sub-step is extending `ToolContext`
   with a server-derived `actorId` and optional `conversationId` (builder methods;
   defaults keep existing call sites/tests unchanged). `memory_recall` has **no**
   Rust FTS/reranking; a deterministic filtered fallback would diverge from
   Python's ranked recall, so either port the retrieval ranking or keep recall
   Python-only (recorded below).
2. **Store-backed tasks/wiki/rss reads** (`list_tasks`, `create_task`, `parse_cron`,
   `read_wiki`, `search_wiki`, `rss_list`, ...): same store-handler architecture;
   `rss_fetch`/network stay excluded.
3. **Filesystem/skill/plan** (`list_skills`, `use_skill`, `plan_step_update`):
   skills are plugin-`SKILL.md`-based in Rust vs filesystem-discovered in Python,
   so parity needs a decision on the skill source; `plan_step_update` can alias
   `update_plan`.
4. **`spawn_subagent`**: needs the tool to reach the subagent executor, which the
   agent runtime does not own; a design item (tool facade vs runtime callback).

**Out of parity scope (recorded, not omissions).** Network tools (`web_search`,
`web_fetch`, `github_*`, MCP management/registry, `rss_fetch`), the parked
optional-ML tools (`image_analyze`, `ocr_extract`, `deep_research`), Python-only
execution (`python_execute`, `bash_execute`, `git_*` wrappers) and
agent-constructor `macro_*` tools are excluded from the M11 expansion: the network
ones were re-scoped in Increment 17/WS1d, the ML ones are parked in
`docs/backlog/python-workers.md`, and macros have no Rust executor (their step
selection composes Python tools). `tools.list` can therefore never contain them
while Python executes them, which is why the picker cutover is staged with the
expansion rather than done now.

**Architecture.** Store-backed handlers live where the CLI can construct them
(`cool-cli`, which already depends on `cool-store` + `cool-agent`) and are
registered in `extension_registry` only when `--legacy-store` is configured;
`cool-agent` gains no new dependency. Handlers read the actor/conversation from
the extended `ToolContext`, mask results through the existing event-sink path,
and map store errors to `ToolResult::error` codes.

**Staged plan (next increments).** 22: extend `ToolContext` (actor/conversation)
+ register `entity_lookup`/`memory_list`/`memory_forget`/`memory_update` with
tests; 23: `memory_remember` (scope handling) + working-memory tools; 24: decide
`memory_recall` (port ranking vs Python-only) and the task/wiki read families;
25: cut `subagents.listTools` to the canonical catalog for the Rust-executed
configs, and re-evaluate `constructor.tools` once the profile/macro execution path
is decided. The pickers stay deferred until their names are covered.

## Data and security

- The HTTP facade never opens SQLite directly: commands go through the same
  actor-scoped `AppServer` dispatch as other transports.
- Fail-closed ordering: profile validation happens before binding, so a
  misconfigured `server` deployment cannot start; request bodies are capped at
  the 1 MiB protocol frame limit; `local` refuses non-loopback peers, opaque
  origins, and cross-origin reads as well as mutations; `server` requires an
  exact Origin whenever one is present and a mandatory Origin on mutations.
- The connection-pool cap (`503` when full) bounds the resource cost of forged
  client identities; identity creation no longer serializes all clients behind
  one handshake, and an unauthenticated request that would mint a new identity
  is refused on the SSE endpoint (`403 client_identity_required`) unless a
  token is configured. A browser without the `cool_client` cookie cannot open
  a stream at all, which closes the cross-site no-cors GET path.
- No new secrets are logged or returned; `ServerConfig`'s secret-presence-only
  `Debug` is unchanged. No `unsafe` code (workspace forbids it).

Increment 2:

- One-way projection, no dual write: `session.for_conversation` reads the
  legacy store but writes only `rust_*` tables. The canonical session is the
  only place new turns will be recorded after the frontend cutover; the legacy
  `messages` table is never modified by the Rust runtime.
- Identity: the command carries no actor field; the actor is derived by the
  server (`local_actor()` today, transport identity is an M11/M12 follow-up),
  and the link table + run listing reject a foreign actor with
  `ActorMismatch`. `deny_unknown_fields` on all three param types keeps payload
  fields from smuggling identity.
- Idempotency: same actor+key replays the stored `ConversationLink`; a changed
  fingerprint raises `idempotency_conflict`; a different key on an existing
  link returns `created=false` with no second import. Concurrency is proven
  across four separate SQLite connections (exactly one creator, one import
  run).
- Secrets: imported event content goes through `masked_envelope`, and
  `rust_runs.finish_reason` is now derived from the masked envelope as well.
  Imported `occurred_at` values are parsed with a year bound (1..=9999) so
  crafted timestamps cannot overflow the civil-date math.
- Bounds: the import window is capped at 10 000 newest messages by a single
  indexed query and reports `truncated`; `conversations.messages` rejects
  out-of-range limits; `session.runs` is bounded by the negotiated
  `event_page_limit`. Oversized RPC frames still fail closed.
- Data ownership: SCHEMA_VERSION 1 -> 2 is additive (`rust_conversation_links`
  + index); a v1 database upgrades in place with sessions/runs/events intact
  and a newer-than-supported version still fails closed.

Increment 3:

- Identity stays actor-scoped: `run.subscribe` and `session.history` read the
  run/session through `local_actor()` and the store re-checks ownership
  (`ActorMismatch`), so a subscriber can only follow a run it already owns; the
  subscriber map is keyed by run id, which is safe while the local facade is
  single-actor (the `server` profile's multi-actor work must revisit this).
- Fan-out cannot bypass masking or frame limits: subscribers receive the
  already-masked, already-persisted `EventEnvelope` that the run sink produced
  after `mask_canonical_event` and `preview_event_frame_fits`, and only the
  owner-send path was reordered (fan-out now happens before the owner send) so
  a failed owner delivery cannot withhold a terminal from subscribers.
- Planning mode is fail-closed: the caller's `systemPrompt` is dropped and the
  runtime directive is used, so a caller cannot steer plan generation. The
  prompt is used only for the model request and is never persisted.
- Pagination is bounded and group-safe: `session_event_window` reads
  `limit + 1` rows per chunk on the append-only `rust_events.rowid`; the
  history read walks until the window starts at a non-delta event, and a
  pathological unbroken delta run beyond the scan cap fails closed with
  `session_history_scan_limit` rather than dropping content.
- `rust_events` rows are append-only and never deleted or vacuumed by the
  runtime (no `DELETE FROM rust_events`/`VACUUM`), so the rowid cursor is
  stable for the lifetime of the store; a future compaction would need to
  switch the cursor to `event_id`.
- No new secrets are logged; the caller system prompt is never written to
  events. No `unsafe` code.

Increment 4:

- The frontend boundary is the canonical protocol only: every translated chat
  operation goes through `AppServer` dispatch (same actor scoping and store
  rules as the stdio/TUI/ACP transports), and the browser identity is the
  HttpOnly `cool_client` cookie; `HttpTransport` uses `credentials:
  "same-origin"` and no command payload carries identity.
- The bearer token (when configured) is sent to both `POST /api/rpc` and
  `GET /api/events` via `Authorization`, never the URL. Tokens passed through
  `VITE_COOL_API_TOKEN` are compiled into the SPA bundle, so the `server`
  profile must serve that bundle behind its own auth boundary.
- The transcript read is bounded: `session.for_conversation` uses a stable
  per-conversation idempotency key so repeated/polling reads replay the durable
  link rather than re-projecting up to 10 000 legacy messages; `session.history`
  is bounded by the negotiated page limit, and the per-run model lookup is a
  single bounded first-event read per run that cannot outlive its `run.started`.
- History projection cannot leak usage across runs (`pending_usage` resets on
  every run boundary) and cannot split a reasoning group across pages (assistant
  items and `usage.updated` are group-internal boundaries).
- No new secrets are logged or persisted; the attachment fallback is the only
  path that still talks to the Python runtime, and it carries no new identity.

Increment 6:

- `tools.list` and `tasks.templates` take `EmptyParams` (`deny_unknown_fields`),
  read no actor field and touch no store, so identity cannot be smuggled through
  them and they work without `--legacy-store`.
- The tool catalog projects only `name`/`description`/parameter-schema/
  capabilities plus the runtime's default-decision-derived `dangerous` flag; it
  never reads `ToolContext.environment`, workspace paths or secrets.
- `tasks.templates` is static runtime data; no user input or store row is read.
- `dangerous` is a runtime-relative definition ("default decision is `Ask`"),
  not a copy of Python's explicit per-tool attribute; it is fail-safe (never
  marks an `Allow` tool dangerous) and not rendered by the UI today.
- The pickers are not cut over precisely because the Python executor would
  silently drop the Rust-only tool names, avoiding a latent mis-configuration.

Increment 7:

- `schedule_description`/`next_runs` are derived only from the task's own cron
  expression and the current clock, using the same bounded parser as
  `tasks.parse_cron`; a malformed expression yields no derived fields rather
  than an error, and the read path never panics on a bad cron.
- Template expansion resolves the slug against the fixed in-process static
  catalog (`task_templates()`), not a filesystem or DB lookup, so there is no
  path traversal or injection surface; an unknown slug fails closed with
  `invalid_input`. A template can only supply its own fixed prompt/cron/tools/
  channels and cannot widen capabilities or approvals.

Increment 8:

- The provider response carries only the masked hint (first 3 / last 4 chars),
  never the key. A decrypt failure yields the literal `<undecryptable>` (the
  same signal Python returns) and a missing key yields `None`, so a corrupted
  ciphertext cannot be confused with a valid key. The key is decrypted only to
  derive the hint and is not logged or persisted.

Increment 9:

- Authorization parity: the task's `capability_policy` narrows the core policy
  (never widens) and `deny_external` denies `send_external`; other approval-gated
  tools auto-approve, matching the Python background-run contract. A task cannot
  widen capabilities or approvals. `tasks.run` is idempotent on `(actor, key)`
  through `LegacyStore::run_idempotent_async`, so a replay returns the original
  run without a second execution.
- Enqueue failures clear the in-flight mark (`Scheduler::complete`) so a task
  cannot wedge as permanently "overlap"; a failing task no longer aborts the
  rest of the tick.
- The executor is actor-scoped to the local single-user actor, matching the
  rest of the local facade; the `server` profile must revisit multi-actor task
  scheduling. Task rows are only writable on a Rust-owned store
  (`--legacy-store` on a Python-owned DB is read-only), so the executor cannot
  mutate a foreign store.
- Run output is secret-masked before persistence; the `CollectSink` does not
  persist to `rust_events`, so the durable `task_runs` row is the record of a
  background run (see Residual risks).

Increment 10:

- **Documented legacy-write exception.** `subagents.launch` writes the isolated
  child conversation's `conversations`/`agent_runs`/`messages` rows because the
  React subagent UI reads the child transcript through `subagents.runs_get`.
  This is the one sanctioned exception to "Rust never writes the legacy
  `conversations`/`messages` tables"; it is safe because the Rust runtime only
  ever runs against a Rust-owned store (a Python-owned DB is opened read-only by
  the CLI), so there is no concurrent Python writer and no dual write. All other
  Rust surfaces remain read-only on the legacy transcript. The exception is
  recorded here; the migration plan's single-writer rule is preserved (one
  runtime owns SQLite writes at any moment).
- Authorization parity: a role/profile `capability_policy` narrows the core
  policy (never widens); unknown capability/decision names are ignored and only
  `"*"` sets the wildcard. Approval-gated tools auto-approve because a launched
  subagent has no interactive approval channel. Invalid working directories fail
  closed. `launch`/`launch_batch`/`runs_cancel` are idempotent on `(actor, key)`
  through `run_idempotent_async`.
- Secrets: the child transcript masks assistant content, thinking, tool-call
  arguments and tool results (`mask_json`/`mask_secrets`) before `add_message`;
  the `result_summary` and error text are masked; canonical parent events are
  masked by `append_event_auto`. A terminal cancellation is not overwritten by a
  late completion (`finalize_subagent_run`), and cancelling a terminal run is a
  no-op.
- Identity stays server-derived (`local_actor()`); the params carry no identity
  (`deny_unknown_fields`), and `cancel` authorizes the run before signalling the
  live cancel channel. The live cancel map is a `std` mutex with a `Drop` guard,
  so a panic in the executor task cannot leak an entry.

Increment 11:

- The replay is actor-scoped: `get_webhook_event`/`get_endpoint` validate the
  event and its endpoint against the caller before any dispatch, and the
  mutation is idempotent on `(actor, key)`. The inbound receive path stays
  intentionally actor-unscoped (loopback/HMAC-authenticated), unchanged.
- `signature_valid` is forced true on the replay row (Python parity: a replay is
  an operator action, not an external arrival), and a dispatch failure records
  `failed` with the error instead of reporting success. The ad-hoc path creates a
  **disabled** one-shot task, so a replay cannot start a recurring schedule.
- The event payload substituted into the ad-hoc prompt is capped at 4000 chars
  and the prompt is stored/masked like any task prompt; the task executor already
  applies the task capability policy and masks run output.

Increment 12:

- The plan run is actor-scoped: `plans.execute` loads the plan through
  `get_plan` (conversation ownership), the session is resolved/reused through
  the existing conversation link, and the run is registered for the calling
  connection. Plan execution is idempotent on `(actor, key)`.
- The plan is transitioned to `executing` synchronously so a second
  `plans.execute` (including after a cancel cleared the session's active run)
  cannot start a concurrent execution. `plans.cancel` is honoured at each step
  boundary and the finalizer never overwrites a terminal plan; a step that stops
  because of a cancellation yields a `cancelled` plan/run, not `failed`.
- Model-supplied titles/steps are persisted through the parameterized
  `create_plan` (JSON array validated); step result summaries and every canonical
  plan event are secret-masked before persistence. The delegate path resolves the
  role by name and caps the child at 900 s, cancelling it on timeout or plan
  cancel so it cannot outlive the plan. The durable plan id is stamped only for a
  conversation-linked session (`conversation_id_for_session` fails closed on a
  foreign actor), and one run persists at most one draft.
- Direct plan steps run with the conversation model/history and an auto-approved
  bounded `AgentRuntime` turn (5 iterations); the step capability policy is the
  core policy (plan steps were already approved as a whole).

Increment 13:

- The compaction mutation is actor-scoped (conversation ownership via the
  resolved session) and idempotent on `(actor, key)`; the source is the
  actor-owned canonical transcript.
- The summary is secret-masked (both the provider output and the deterministic
  fallback, masked before truncation) before it reaches `working_memory` or the
  canonical event, and it is hard-capped (`max_tokens = 1000`, 8000 chars) so a
  pathological summary cannot exceed the transport frame and break
  `session.history`.
- The canonical projection runs before the legacy `working_memory` write and its
  error is propagated, so the two stores cannot advance independently and a
  failed compaction is retryable. The previous-summary cutoff is read from the
  canonical `role: "summary"` item (one cursor space), so a store compacted by
  Python/old-Rust is re-summarized rather than silently skipped.
- `session.compacted` carries only the masked summary and a cursor; the stream
  JSON projection omits the summary text, so the live event cannot bypass the
  transcript read.

Increment 14:

- The facade's `run.subscribe` is actor-scoped by the runtime
  (`store.run(run_id, actor)`), so a browser can only follow a run its identity
  owns; under the local single-actor facade every `cool_client` maps to
  `local-user`, which is the same single-user trust boundary as the rest of the
  facade (the `server` profile's multi-actor work must revisit this, as recorded
  in Increment 3).
- Fan-out delivers the already-masked, already-persisted `EventEnvelope` the run
  sink produced (after `mask_canonical_event`/`preview_event_frame_fits`), so
  the new subscribe path cannot bypass secret masking or the frame-size guard.
- Subscribing registers this connection in the app-server's per-run subscriber
  map. A browser that abandons its SSE stream before the run terminates leaves a
  registration until the run reaches a terminal state (which removes it) or the
  protocol connection disconnects; the map is bounded by live runs, and a
  subscriber whose HTTP stream is gone simply has its notifications drained into
  a broadcast channel with no receiver. Recorded as a residual.
- The subscribe response's `terminal` flag is advisory only: correctness still
  relies on the durable terminal event (or the post-registration re-read in the
  app server), so a race between the flag and the terminal fan-out cannot drop
  events or hang the stream.

Increment 15:

- The OpenCode worker is untrusted even when locally installed (M0 threat model):
  it runs in its own process, receives no DB handle, master secret key or
  ambient environment (the launcher rejects reserved names and allows no secret
  through; `WorkerProtocol::spawn` additionally clears the environment to the
  minimal baseline plus sanitized values), and reaches the core only through the
  versioned RPC. `run.subscribe`-style state ownership is unaffected.
- Isolation is enforced before spawn: the install root and data root must be
  real (non-link) directories and must not contain one another; the entry must
  canonicalize inside the install root, be a regular non-link file and carry an
  allowed JS/TS extension; granted workspaces must be canonical existing
  directories that do not overlap (contain or sit inside) the install root. This
  blocks symlink/path-traversal escapes and accidental install-tree writes
  through the worker's cwd; it is **not** a filesystem sandbox — the plugin runs
  with the user's OS rights and could still write absolute paths — so
  install-tree integrity relies on the install root being separate and, for
  store-installed plugins, content-hash verified. The writable data root is
  created on demand (it carries no install-time integrity). The untrusted-worker
  boundary (no DB handle, no secrets, no ambient environment, no capability
  widening) is unchanged.
- Capabilities are mapped, never widened: `opencode_worker_policy` is a
  narrowing child of the core policy and denies undeclared capabilities; the
  launcher fails closed (`CapabilityDenied`) when the core denies a required
  capability. There is still no worker tool-facade call surface in this
  increment, so the mapping is preparatory and cannot grant anything today.
- A spawn failure, invalid tree or denied capability is reported as a visible
  plugin/worker status event; it does not abort `cool serve`/`app-server`, so the
  base install is never gated on Bun. No secret is logged: the reported error is
  the launcher's structured message (paths/capability), not environment values.

Increment 16:

- Adoption is the single point where Rust becomes the migration owner: it takes a
  verified backup before the first Rust write and records the owner marker, so
  the pre-adoption snapshot is always recoverable (`restore_backup`). The
  operator must run `cool store adopt` explicitly; `serve`/`app-server` never
  adopt as a side effect, so a Python-owned store cannot be silently mutated and
  Alembic/Rust migrations never run concurrently (one writer at a time).
- The runtime image runs as non-root uid 10001 with a single writable data
  volume; the entrypoint is `tini` so signals reach the one process. No Python,
  Node or Bun is installed, so no interpreted plugin runtime can execute from the
  image by default.
- The container's non-loopback bind requires a token; without `COOL_API_TOKEN`
  the server refuses to start (fail-closed), and the token is read from the
  environment, never baked into the image or the SPA bundle.
- `cool store adopt` reports only paths/counts/booleans (database path, backup
  path, revisions) — no row contents or secrets.

Increment 17:

- The new surface is read-only and actor-agnostic: `extensions.status` takes
  `EmptyParams` (`deny_unknown_fields`), reads no actor field and mutates no
  store, so identity cannot be smuggled through it and it cannot change plugin,
  hook, MCP or capability state. MCP tool policy is reported for visibility
  only; nothing in this command can widen a capability or reach the DB/auth
  store/supervisor.
- The snapshot is secret-free by construction: it carries install metadata,
  parsed skill metadata, hook `trust_hash`/review state and MCP endpoints only.
  `McpServer::Stdio` reports the command path and `StreamableHttp` the URL; no
  `env`/`headers` values (which may carry tokens) are projected.
- A failed host read is a canonical `extension_state_failed` with a *masked*
  error detail in `safe_details`; it never degrades to an empty catalog that
  could be mistaken for "nothing installed". The CLI implementation only reads
  through `PluginStore`/`ExtensionRuntime` (the same objects the lifecycle uses)
  and never opens a second writer.

Increment 18:

- Both mutations are narrowly scoped to the M8 extension store: they write only
  `plugins.lock.json`/`hook-reviews.json` (and the admin audit log) under the
  store's file lock. They take no actor field from the caller — the app server
  supplies the server-derived `local_actor().id` — cannot widen a capability,
  cannot touch the SQLite/durable store, the auth store or the worker supervisor,
  and cannot reach the network.
- Enabling a plugin re-verifies its content hash and fails closed on a tampered
  tree; approving a hook requires the submitted trust hash to equal the current
  declaration's hash, so an approval for a different command/args/env/matcher
  fails closed with `extension_mutation_failed` and an audited
  `trust_mismatch`. Reject is an idempotent lock-guarded clear.
- Every mutation attempt is audited with the server-derived actor, action,
  target, trust hash and outcome; the audit append is lock-guarded and
  best-effort (a failed append does not roll back or mask the mutation). No
  secret or raw environment value is written to the audit log.
- Mutations are naturally idempotent (same enable/review state → same state); the
  protocol still carries an idempotency key. No new secret is logged or returned;
  failures carry only a masked detail.

Increment 19:

- The page is a read + two existing mutations over the canonical protocol: it
  sends no identity (the server derives the actor) and cannot widen a capability.
  It only calls the three `extensions.*` commands through the generated SDK; the
  former Python MCP/skills REST modules are untouched and still used by their own
  pages, so no new transport or endpoint is introduced.
- Error copy is derived from the server's already-masked `safeDetails.detail`
  (the page never renders a raw protocol frame).
- The UI deliberately blocks enabling a `contentVerified:false` plugin, mirroring
  the server's fail-closed behaviour, and shows the tamper state so an operator
  cannot enable a tree the runtime would reject.

Increment 20:

- The system prompt is operator-authored configuration, so it is stored as-is
  (masking would corrupt it) and is never logged or written to the durable event
  log; it is used only for the model request, matching the existing
  "prompt is never persisted" rule. The settings file is bounded (100k chars) and
  written atomically; a corrupt file fails closed rather than resetting.
- The params carry no identity (`deny_unknown_fields`); the settings commands take
  no actor and cannot widen a capability. The default prompt is applied as a
  system message, not interpolated into tool arguments or shell commands, so a
  prompt cannot escalate execution.
- `settings.system_prompt_set` is idempotent (writing the same value twice yields
  the same file); an oversized prompt is rejected before any write.

Increment 22:

- The store-backed tools take the actor from `ToolContext` (set server-side),
  never from tool arguments, and `reject_unknown` rejects unexpected fields, so a
  model cannot address another actor's memory rows. The store methods are
  actor-scoped (`user_id_for`), so cross-actor reads/writes fail closed.
- Tool output is `.masked()` before it reaches the event log (the run sink also
  masks), and store errors are surfaced as a literal `memory_store_failed` code
  with the store message (no secret present in those messages).
- The tools are registered only when the CLI serves a legacy store; without
  `--legacy-store` the agent has no memory tools, so a store-less install cannot
  read or write the memory tables. Memory tools use `Decision::Allow` and no
  capabilities, matching the Python registry (Python's memory tools are not
  approval-gated).

## Independent review

First pass `m11_web_facade_review` (read-only, not the author) inspected the
full diff and untracked files, ran `cargo test -p cool-http -p cool-cli` and
clippy, and probed the built binary on loopback. Findings and resolutions:

1. **P1 — local CSRF bypass via `Origin: null`.** An unparseable/opaque Origin
   was treated like an absent Origin, so a sandboxed/`data:` page could POST to
   a tokenless local server. Fixed: `origin_allowed` rejects any
   present-but-invalid Origin and duplicate `Origin` headers; regression tests
   `opaque_and_duplicate_origins_are_rejected` and
   `opaque_origin_is_rejected_in_local_profile`.
2. **P2 — unauthenticated pool exhaustion, slots never released.** Accepted
   residual risk (below): the Origin fix removes the cross-site path, and a
   co-located process already has OS-user access. The cap is kept so exhaustion
   is at least bounded and visible.
3. **P2 — SDK identity is cookie-dependent; the Node/live-stream claim was
   overstated.** The SDK header now states Node callers must reuse one
   `clientId` across `HttpTransport` and `streamRunEvents`, since events are
   delivered to the connection that started the run.
4. **P2 — bearer token placed in the SSE URL.** Fixed in the SDK (sends
   `Authorization`); the facade keeps `?token=` only for native `EventSource`.
5. **P3 — duplicate `Display`/non-exhaustive match and dead old body** were
   introduced while adding `LimitReached`; fixed.
6. **P3 — constant-time compare returns early on length mismatch.** Kept:
   token length is not a meaningful secret for a ≥16-char high-entropy token,
   and length-independent comparison of unbounded inputs is not standard.
7. **P3 — IPv6 loopback origins rejected.** Fixed by stripping the
   `Uri` authority brackets before `IpAddr` parsing; test
   `ipv6_loopback_origin_is_allowed`.

## Residual risks

- Each distinct `cool_client` identity holds a live protocol connection for
  the process lifetime. The pool is bounded at 128 and refuses new identities
  when full, but there is no idle eviction yet: a legitimate long-lived
  deployment with many browsers would need eviction with run-safety analysis,
  and (accepted) a local caller can occupy all 128 tokenless-local slots for
  the process lifetime. That caller can be a co-located process (which already
  has filesystem access) or, because `localhost` is itself a loopback origin,
  a *different local web app* (`http://localhost:3000`) whose `POST /api/rpc`
  mints identities. Non-loopback/opaque origins and anonymous SSE are refused,
  so this is not remotely reachable; it is the accepted cost of a tokenless
  single-user local default.
- The SSE stream cannot know locally that a run is already terminal when the
  requested cursor is already past the terminal seq, so it stays live and
  emits keepalives instead of a synthetic terminal frame. Clients that know
  the run finished should close the stream.
- `?token=` auth for `EventSource` places the token in the URL (and thus
  access logs); the `Secure` cookie path is preferred where a login flow can
  set it. Recorded here because the server profile currently has no login flow.

Increment 2:

- A legacy tool row whose result matches no pending assistant call (corrupt or
  hand-edited store) is still projected as a standalone tool role; matched
  results are normalized, and leading orphans are trimmed, so only
  mid-transcript corruption can produce it.
- The import window is bounded at 10 000 newest messages; the truncation path
  itself is implemented and reported via `truncated`, but no integration test
  seeds more than 10 000 messages (the `recent_messages` boundary logic is unit
  tested instead).
- A rebind with a new idempotency key reports `created=false`,
  `imported_events=0` and the *current read's* `truncated` flag, so
  `truncated=true` with `created=false` is a valid response.
- Imported `occurred_at` keeps whole-second precision (`.000Z`); durable order
  comes from run/seq, not the timestamp.
- The oversized-frame test now configures 1024 bytes because the initialize
  response grew with the two new capabilities; a much larger capability list
  would require the test limit (or the handshake budget) to be revisited.
- The import read/projection runs synchronously on the async dispatcher, like
  the rest of the legacy family dispatch; one very large source conversation
  can stall the connection task while it works (bounded to one indexed window
  query plus mapping).
- `parse_python_datetime` now rejects years outside 1..=9999, but the public
  `days_from_civil` helper itself still uses unchecked arithmetic; all current
  callers pass bounded values (latent API hazard only).

Increment 3:

- The history cursor is `rust_events.rowid`. The runtime never deletes or
  vacuums events, so it is stable today; any future store compaction must move
  the cursor to `event_id` before it renumbers rows.
- `session.history` is newest-first pages; the walk stops at a non-delta group
  boundary, so a page whose oldest group exceeds the scan cap fails closed
  (`session_history_scan_limit`) rather than returning partial reasoning. A
  legitimate turn with an enormous reasoning stream could therefore be
  unreadable through this command until the client lowers `limit` (which raises
  the cap proportionally).
- Fan-out is sequential and awaits each subscriber's bounded send, so one slow
  subscriber can briefly delay the owner's run sink and other subscribers; the
  subscriber map is keyed by run id and assumes a single actor, which is safe
  for the local facade but must be revisited when the `server` profile
  introduces multiple actors.
- The HTTP/SSE facade now calls `run.subscribe` (Increment 14), so a browser on
  a second identity can follow a foreign run through the facade
  (`a_second_identity_streams_a_foreign_live_run_through_run_subscribe`). A
  subscriber whose HTTP stream is abandoned before the run terminates leaves a
  per-run subscriber registration until the run reaches a terminal state or the
  protocol connection disconnects; it is drained into a receiver-less broadcast
  channel in the meantime. This is bounded by live runs and self-clears, but
  there is no explicit per-stream unsubscribe command yet.
- A canonical run whose events are written without live fan-out (today: the
  subagent executor's auxiliary parent-lifecycle run, which uses
  `append_event_auto` rather than a `RunSink`) can be replayed through
  `run.events` but cannot be followed live: a browser that opens
  `GET /api/events` for it registers as a subscriber and then receives only
  keepalives until it disconnects, because no `publish_to_subscribers` call ever
  fires for that run (the `already_terminal` path only ends a run that was
  already terminal at subscribe time). This is pre-existing and has no React
  consumer (the subagent dialog polls `subagents.runs_get`); a future consumer
  must either wire the lifecycle sink to fan out or the facade must re-check the
  durable status on its live idle timeout. Recorded rather than fixed because
  the facade cannot manufacture a terminal the runtime never publishes.
- The fan-out test holds a run with a gated tool; the disconnect-cancel
  terminal fan-out test uses a long provider delay. Both are deterministic
  under normal load but the disconnect test still depends on cancellation
  racing the delayed provider.
- `bounded_history` could in principle return `has_more=true` with no
  `next_cursor` if a bounded window projected to zero items; the walk only
  stops at a group boundary that always projects to an item, so this is
  unreachable today, but a client should treat a missing cursor as terminal.
- The approval-request fan-out in the approval gate publishes before the owner
  send, so a subscriber sees `tool.approval_required` even if the owner has
  disconnected; the waiter still fails the run closed when the owner cannot be
  reached, so the run does not hang.

Increment 7:

- Timezone handling diverges from the Python read path for fixed offsets and
  named IANA zones: the Rust store interprets `+03:00` as a real offset (so a
  `0 8 * * *` task derives `05:00Z` and its `next_run_at` matches), while Python

  for IANA names. This is the pre-existing M10 timezone scope (UTC + fixed
  offset in Rust, documented there), now surfaced through the derived
  `next_runs`; the canonical Rust read is internally consistent with the Rust
  scheduler, which is the runtime we are cutting over to.
- The read path maps a Rust-unknown/IANA timezone to UTC (`unwrap_or(0)`) while
  the scheduler engine fail-closes such a zone; a Rust-created task therefore
  always has an interpretable zone, and the asymmetry only affects imported rows.

  accepts a 6-field (seconds) form. A task imported from Python with a
  seconds-field cron therefore gets no derived `schedule_description`/
  `next_runs` in Rust (the raw expression is preserved). Tracked for the cron
  parity work.
- An unknown `template` slug fails with the JSON-RPC `invalid_input` code
  (-32602) rather than Python's HTTP 404; the canonical error model has no
  404-mapped code and no in-tree consumer keys on the HTTP status.
- Derived timestamps are formatted like `tasks.parse_cron`
  (`…T08:00:00.000000Z`); Python emits `…:00Z`. Both parse identically in the
  browser (`new Date(…)`), so this is cosmetic cross-runtime drift.
- The canonical `tasks.create` ignores the template's `max_iterations`
  (`preset.max_iterations`), matching the Python endpoint's `body.max_iterations`
  (default 10) but diverging from the template's advertised value in the UI.
- `tasks.update({workflowType})` is still always sent as `null` by the frontend,

- `list_due_tasks` is not actor-scoped while run writes use the local actor, so

- Per-task `profile_id`, `workflow_type` (deep research) and delivery channels

- Background task runs do not project into `rust_events`, so they are absent
  from the inspector/analytics and their spend does not reach budgets; the
  durable `task_runs` row is the record. The `CollectSink` also returns a
  placeholder envelope and never persists.
- A panic inside the agent runtime/tool leaves the task's in-flight mark and the
  `live` cancel entry set (the cleanup runs only on normal completion).
- A cancel resets the task's `failure_count` (the store outcome API takes a
  success boolean) instead of leaving it unchanged as Python does, so an
  alternating fail/cancel sequence cannot auto-disable a task in Rust.
- A due task whose quiet-hours window names an unsupported (IANA) timezone is
  dropped from the tick with a best-effort skipped run; if it cannot be
  rescheduled (`record_skipped_run` recomputes the same unsupported schedule)
  it remains due and is re-examined every tick without running.
- `tick`, `spawn_loop`, `record_skipped_run`, live cancel and the

Increment 10:

- `launch_batch` resolves every item before writing, but the per-item row
  creation is not a single transaction: a failure after the first item (e.g. an
  unexpected store error) leaves the earlier child conversations/runs behind and
  the idempotency reservation in `pending`, so a retry with the same key fails
  closed with `conflict`. The resolve-stage failure path is tested; the
  mid-batch write-failure path is not.
- The parent canonical lifecycle projection is best-effort: a conversation whose
  parent was never linked to a canonical session (`session.for_conversation`)
  produces no `subagent.*` events (a no-op sink). The auxiliary lifecycle run is
  closed on the normal terminal path only; a process crash before
  `close_lifecycle` leaves it `running` until `recover_incomplete_runs` runs at
  the next server construction. Auxiliary runs are visible in `session.runs`.
- Subagent tool calls auto-approve (no interactive approval channel), matching
  the background task executor; a role/profile policy can only narrow. The live
  cancel map and the auxiliary-run addressing assume the local single-user
  actor; the `server` profile must revisit multi-actor identity.
- `parent_run_id` is optional metadata at v1 and is not validated to reference
  the same conversation.
- Approval/capability-policy denial paths and a live cancel of a tool-in-flight
  subagent are not directly tested; the cancel test uses a delayed provider
  rather than a gated tool (it asserts the aborted run produced no assistant
  transcript row, which fails if the live signal is dropped).
- The parent lifecycle events live on a dedicated auxiliary canonical run, and
  the chat client streams a run by id, so a live chat turn does not render them
  inline; they are durable and readable through `runs.events`/`session.runs`
  (the React subagent page polls `subagent_runs`, not the canonical run). The
  distinct cancelled rendering only applies where those events are consumed.

Increment 11:

- The ad-hoc one-shot task is created with the store's default `timezone` (UTC)
  rather than the configured scheduler timezone; it has no quiet-hours window, so
  there is no functional effect today.
- The replay is not a single transaction across the new event row, the task run
  and the event status update: a crash can leave a `processing` event or a
  disabled task behind, and an idempotency-reservation write failure after a
  successful dispatch makes the key permanently unretryable (the M10
  at-most-once contract). A retry fails closed rather than duplicating the run.
- A missing linked task records the store's generic `task not found` error
  rather than Python's `Linked task {id} not found` text.
- `dispatch_task`/`dispatch_adhoc` take an `ActorRef` but the underlying
  `enqueue`/`execute` use the local actor; safe for the local single-user facade
  and must be revisited with the `server` multi-actor work.

Increment 12:

- A plan execution and the model-plan turn share the conversation's canonical
  session/event log; the plan run is a second run in that session. `plans.cancel`
  is only observed at step boundaries, so the currently-running direct/immediate
  step is not interrupted mid-step (Python `cancel_plan` also does not stop a
  running step).
- Direct steps use a bounded 200-message legacy history with user/assistant
  turns only (tool rows are skipped) rather than Python's full `load_history`,
  and run with `max_iterations = 5` and auto-approved tools.
- The delegate path waits up to 900 s for the child subagent and cancels it on
  timeout/cancel; it does not set `plan_steps.run_id` (Python never links it
  either).
- `planned_runs` keeps one durable-draft id per active run and clears it on the
  run's terminal event; a plan run that terminates without a terminal event
  (process crash) leaves the entry until the process restarts.
- `storePlanId` is additive at v1 but is always emitted, so a strict older v1
  decoder with `deny_unknown_fields` on results would reject a `plan.created`
  event (the same versioned-peer caveat as other additive fields).
- Plan execution is actor-scoped to the local single-user actor; the plan run
  and its cancel map assume the local facade and must be revisited with the
  `server` multi-actor work.
- The `plans.execute` replay check is a read outside `start_run`'s transaction:
  two same-key requests racing can make the loser return `invalid_input` instead
  of the original run (no second execution is possible).
- A cancellation observed after a step failed breaks the loop without writing a
  status for the in-flight step, so it can be left `running` in the DB while the
  plan is terminal (Python leaves a cancelled step similarly unsettled).
- A conversation without a model silently falls back to the server default;
  Python returns 400 for a plan whose conversation has no model.
- Direct steps cap the context at the newest 200 user/assistant legacy messages
  (tool rows skipped) and use `max_iterations = 5` with auto-approved tools.

Increment 13:

- The canonical item count can be lower than Python's message count (the import
  drops content-less user/assistant rows and projects tool rows), so the exact
  30-item boundary is approximate across the two runtimes.
- `collect_session_items` walks at most 64 pages (≈6400 items): a very long
  conversation summarizes only the newest window and never reaches the oldest
  items. There is no truncation signal.
- Every compaction appends a new `session.compacted`/summary item; the protocol
  contract is "newest wins" (the chat dedupes by cursor), but a non-frontend
  consumer of `session.history` sees the overlapping summaries accumulate.
- `session.compacted` is appended on an auxiliary run, so it is durable and
  readable but is not delivered on the active chat run's SSE stream; the UI
  refreshes from the transcript after compaction.
- A store compacted by Python or old-Rust has no canonical summary item, so the
  first Rust compaction re-summarizes the whole older prefix once (no data loss,
  redundant tokens) and the legacy `working_memory.summary_up_to_message_id`
  column is left NULL.
- Compaction resolves the model from the conversation/default (no
  `memory_summary_model` equivalent) and uses `temperature = 0.0` vs Python 0.3;
  the summary affects the transcript UI, not the model context (canonical prompt
  runs still start from empty history).
- A compaction that commits the canonical projection but then fails the legacy
  `working_memory` write leaves a pending idempotency row, so a same-key retry
  fails closed; the canonical summary is already durable.

Increment 15:

- The launcher validates then spawns, so a same-user process could still swap a
  validated directory for a link/reparse point in the window before `spawn`
  (TOCTOU). Low risk in the local single-user model and no more permissive than
  any other locally installed child process; a hardened launcher would hold
  handles across the spawn.
- `sanitize_environment` filters by name marker (`_KEY`/`_SECRET`/...) and would
  not catch names like `GITHUB_PAT` or `DATABASE_URL`; the CLI therefore passes
  an empty environment and explicitly allows no secret, so only the minimal
  process baseline is inherited. A future caller feeding untrusted values should
  prefer an allowlist, not this denylist.
- `opencode_worker_policy` is preparatory: the versioned worker RPC has no tool
  facade yet, so the narrowed policy is computed and fail-closed on denied
  requirements but not yet consulted at request dispatch. It cannot grant
  anything in the meantime.
- The env-gated `COOL_OPENCODE_WORKER` path trusts the operator-supplied entry
  and does not re-verify a content hash or require an enabled/reviewed store
  record; the store path retains those checks. This is acceptable because the
  operator sets the variable, but it is not a supply-chain verification of the
  entry.
- The OpenCode ABI is an experimental subset pinned to the versioned worker
  request/response envelope; unsupported OpenCode runtime/plugin semantics are
  not emulated and the adapter is marked `is_executable()` accordingly.

Increment 17:

- `extensions.status` reports host-global extension state for the local
  single-user actor and, like `status.get`, triggers a worker heartbeat while
  building the snapshot (a read may respawn a failed worker). Both are inherited
  from the lifecycle status path; multi-actor scoping is the `server`-profile
  work.
- `redact_location` strips URL userinfo/query/fragment and masks secret-shaped
  text, but its parse-failure fallback only masks: a syntactically invalid URL
  embedding `user:secret@` would survive. It is reachable only through a
  hand-edited lockfile, because MCP URLs and Git sources are validated at install
  time.
- Plugin-authored fields (`SkillRecord.description`, diagnostic `message`/`path`,
  the `mcp:` hook handler, `PluginRecord.name`/`revision`) and
  `WorkerRecord.code` are not passed through `redact_location`; they are
  config/plugin-authored values, and `WorkerRecord.code` is already exposed
  unmasked by `status.get`.
- `capabilities()` is a static advertisement, so `extension_admin` is listed even
  on a server with no extension host (the `None` arm still answers with an empty
  snapshot rather than an error).
- The admin read loads and hashes every enabled plugin on the request thread, and
  `PluginLoader::load` may create the plugin data/cwd directories as a side
  effect; it reuses the runtime loader rather than a read-only variant. It never
  mutates the lockfile or the plugin installation tree.
- The worker test path uses an app-server fake rather than starting a real
  compatibility worker; the CLI `mcp:` hook-handler variant and a
  matching-hash/wrong-manifest-name bundle are not covered by tests.

Increment 18:

- The two mutations are durable in the plugin store but the already-running
  `ExtensionRuntime` seeds its hooks/MCP clients/review store at startup, so an
  approve/reject or enable/disable takes effect on the next start. Live reload of
  the runtime is not implemented; the review UI must state this.
- The admin audit append is a separate write from the mutation and is
  best-effort: a crash between the mutation and the audit line could leave the
  mutation unlogged, and an audit-append failure does not fail the mutation. It
  shares the store's append lock but is not transactional with
  `plugins.lock.json`/`hook-reviews.json`.
- `extensions.plugin_enabled` accepts an idempotency key but does not persist an
  idempotency record: the underlying store mutation is naturally idempotent, so a
  replay is safe, but a replay is re-executed and re-audited rather than deduped.
- Mutations remain host-global and single-actor (`local-user`) until the
  `server`-profile multi-actor/admin authorization work; there is no per-actor
  authorization check beyond the server-derived actor recorded in the audit log.
- `PluginStore::set_enabled`/`set_hook_review`/`clear_hook_review` are synchronous
  blocking file I/O executed on the async request path (low-frequency admin
  operations; the store's file lock already serializes writers).
- `extension-admin-audit.jsonl` grows without bound (one line per attempt,
  including replays); rotation/retention is deferred.
- The `plugin_not_loadable` and `store_error` audit branches have no dedicated
  test (both are hard to trigger without corrupting the store mid-call).
- `set_enabled`/`set_hook_review`/`clear_hook_review` return early on some error
  paths without an explicit `lock.unlock()`; the `File` drop releases the OS
  lock, so this is harmless but implicit.

Increment 19:

- The UI states (in the mutation toasts) that an enable/disable or hook
  approval applies when the extension host next starts; there is no optimistic
  update and no live reload (Increment 18 residual).
- There is no frontend component-test harness, so `ExtensionsPage.tsx` behavior
  (e.g. approve/revoke state) is covered only by the `protocol:check` AST gate and
  TypeScript; the error-copy branches for `extension_state_failed`/
  `extension_mutation_failed` are unreachable while the server always injects a
  masked `detail`.
- The page still shows the Python-era `profiles.ts`/`constructor.ts` tool pickers
  and the MCP/skills pages on their own transports; Increment 19 only adds the
  extension admin page and does not remove the Python MCP/skills REST modules.

Increment 20:

- Rust has no bundled default-prompt text, so an unset default sends no system
  message (the prior behavior); the Python package's long default prompt is not
  ported (M12 parity item).
- `settings.json` is read on every non-plan turn (a small file read on the async
  path); it is not cached, so an external edit takes effect immediately but adds a
  syscall per turn.
- Multi-writer safety is last-writer-wins: writes are atomic (temp + rename) but
  there is no cross-process lock, and the `settings.system_prompt_set` idempotency
  key is accepted but not persisted.
- Settings are host-global and single-actor (`local-user`); per-actor
  authorization is the `server`-profile work, as with the extension admin.
- The settings file has no integrity/ownership marker (it is plain operator
  config), so a hand-edited file is trusted.
- A corrupt `settings.json` fails closed server-side, but the Settings page
  (`SystemPromptSection`) only observes `{data,isLoading}`, so it shows an empty
  editor rather than an error hint; surfacing that read failure in the UI is a
  polish item.
- The settings length cap is enforced in `FileAppSettings` and has no
  protocol-level test (the CLI store is not available to the app-server test
  crate).

Increment 22:

- `memory_list`/`memory_recall` do not enforce scope/project-key visibility: the
  Rust store's `MemoryFilter` has no scope/project predicate, so an actor sees all
  of its active memories (not only global + this-project + this-agent). Not
  cross-actor; porting the Python visibility projection is a later slice.
- `memory_recall` is a bounded lexical content filter ordered by importance, not
  the Python FTS5 + embedding hybrid ranking; semantic recall stays Python-only
  until the ranking is ported or a vector store is added in Rust.
- Tool result shapes differ from Python's trimmed projections, `memory_remember`
  does not run Python's dedup/`supersedes_id` contradiction logic, and
  `memory_remember` returns the real store status rather than Python's literal
  `"stored"`.
- The store tools are registered only with `--legacy-store`; a read-only
  Python-owned store advertises the write tools and rejects the write at call time
  with a store error.
- `set_working_memory` merges into the state object; a non-object legacy `state`
  is replaced by `{}` on the next set (only this tool writes state, so it is
  always an object), it rejects an empty string key/value where Python accepts
  `""`, its read-modify-write is non-atomic (Python parity), and `serde_json`
  rejects `NaN`/`Infinity` that Python's `json.loads` accepts.
- Only `session.prompt` binds a conversation to the tool context. The direct plan
  step (`execute_plan_step_direct`) and the subagent run also execute with the
  store-backed registry but bind only the actor, so a `memory_remember` from those
  paths writes conversation scope with a NULL conversation id (not a regression —
  they never bound one — but a follow-up for those two call sites).
- The conversation-scope binding has no end-to-end test (it needs a seeded
  conversation owned by the actor).
