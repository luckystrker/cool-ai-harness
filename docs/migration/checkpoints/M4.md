# M4 checkpoint — ACP adapter over Python runtime

Status: **implementation passed; real-client acceptance pending**

Date: 2026-09-01

Scope: local, single-user ACP v1 adapter over the existing authoritative Python runtime. Rust ACP
ownership, multi-process/VPS coordination, network authentication and Telegram identity remain
later migration phases.

## Outcome

`cool acp` now serves bounded newline-delimited JSON-RPC 2.0 over stdio. It implements initialize,
session new/load/prompt/cancel, projects the canonical event stream into ACP content/thought/tool/
permission/plan updates, and persists through the same conversations, runs and append-only events
used by the Web UI. The adapter does not own tool execution or approval state.

The implementation gate is complete, but the roadmap's real-client acceptance gate is not: the
installed local Zed process did not expose a usable window/ACP log in this execution environment.
No successful Zed prompt is claimed. M5 must not treat M4 as fully accepted until a real Zed prompt
and a second external ACP client prompt/continuation are retained as evidence.

## Deliverables

- `cool acp` command with stdout reserved for protocol frames and logs on stderr.
- ACP v1 initialize, `session/new`, `session/load`, `session/prompt` and `session/cancel`.
- Pinned official ACP v1 schema, source revision and SHA-256 provenance.
- Baseline text and ResourceLink prompts; optional media/embedded-resource capabilities disabled.
- Canonical-event projection for messages, thoughts, tool lifecycle, permissions and plans.
- Durable conversation/run/event reuse, replay on load and atomic user-message/run creation.
- Fail-closed permission responses, strict bounded JSON and run-scoped cancellation.
- One-active-turn guard shared by ACP, SSE and WebSocket in the local process.
- Interruptible provider/tool waits and forced process-tree cleanup for async and thread-fallback
  bash, git and Python subprocesses on Windows and POSIX.
- Zed-shaped/reference fixtures plus an actual stdio subprocess initialization smoke.

## Independent review

Independent reviewer: `m3_independent_review`, read-only inspection of the actual working-tree diff
and relevant untracked files. Review-driven passes found and resolved:

1. mutable load cwd, malformed permission authorization, non-interruptible waits, broad approval
   cancellation, missing ResourceLink baseline, misleading usage, non-atomic persistence, permissive
   JSON and overlapping ACP/Web turns;
2. cancel-during-permission failure, tool preflight/completed-operation races and subprocess cleanup;
3. direct-PID-only cancellation and missing process-tree regression coverage;
4. cooperative-only Windows cleanup, cleanup races, timeout cleanup and a false-pass grandchild test.

5. Final focused pass: clean, with no actionable P0-P3 findings. The reviewer also ran the forced
   grandchild cancellation regression: 2/2 passed for async and thread fallback.

M4 remains acceptance-pending despite the clean code review because the external-client smoke
criterion is independent.

## Residual boundaries

- Active-turn and approval registries are process-wide, not distributed. A public/multi-process VPS
  deployment requires durable/distributed ownership and authentication in later phases.
- ACP usage updates are omitted until the canonical context authority can provide the ACP-defined
  current session-context value rather than an invented per-call sum.
- ResourceLink references are passed to model context but never fetched implicitly around normal
  file/network capability checks.
- The protocol is intentionally pinned to ACP v1 for M4; adopting v2 is a separate contract change.
